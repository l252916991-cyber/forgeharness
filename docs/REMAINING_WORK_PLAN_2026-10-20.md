# ForgeHarness 剩余完善与验收计划书

编制日期：2026-10-20；修订日期：2026-10-21  
状态：执行中；R0 基线修复已开始，其他工作包仍按下表推进；最终门禁以绑定源码的报告为准。  
适用范围：当前 ForgeHarness 0.6.0 源码（原 0.5.0 + Unreleased 框架化改动已全部并入 0.6.0）。  
目标：完成受治理的多编排 SDK，用法律与电商两个宿主验证复用，并形成与具体源码绑定的验收证据。

本计划整合当前未完成工作，不重做 F1a、F1b、F0b、F2a、F2b-1、F3a、F3b 子集，以及 2026-10-20 的引用完整性、组合审计和 F1c-1。既有计划保留设计背景；具体实现状态以 [STATUS](STATUS.md)、源码和新候选验证结果为准。

R0 当前验证方式和证据读取见 [候选验证说明](BASELINE_VERIFICATION.md)。本次修复前采集与旧缓存对照已定位为 1116/1123，旧缓存多 7 条名称；新增回归后的测试数量由本轮 JUnit 报告生成。

## 1. 当前基线

### 1.1 已完成，后续应复用

| 能力 | 当前实现 | 后续使用方式 |

| 核心治理 | 预算、工具验证、策略、持久审批、调用日志、checkpoint、恢复、trace、完成验收 | 保留确定性状态所有权，扩展编排时共用这些机制 |

| 法律只读原型 | bundle、SQLite 导出、并行 DAG、页 digest、快照摘要、精确引文校验 | 在真实宿主权限、版本、撤回和专业评审条件下验证 |
| 电商本地流程 | 合成商品、知识版本、会话、咨询、模拟工单和控制台 | 接入真实宿主时替换身份与业务适配器 |
| 公共业务模块 | SessionService、ImportService、TaskRunner、RevisionStore、WorkflowRunner 等 | 验证接入与生命周期，不重新开发一套 |
| 契约测试 | 应用契约及共享运行时子集已存在 | 扩展矩阵，明确适用与不适用项 |

法律只读导出已有一次本地案件运行记录：14 页、5 文档、4 个问题、脚本模型、源数据库摘要不变。这只能证明该次只读链路；不能算真实模型质量、律师验收或完整 LexVault 集成。

当前 `LexVaultDagOrchestrator` 是三类词匹配专家加一次 Critic 的流程原型，尚未接入宿主真实专家和混合检索。导出器本身不负责身份授权；`BundleCitationVerifier` 的 `strict_quotes` 默认关闭。这些都是 R4/R6 要显式处理的接入与评测配置。

## 2. 完成边界与优先级

优先级表示执行顺序，不等同于缺陷严重程度；缺陷仍按 blocker/high/medium/low 分类。

- **P0：基线与发布阻断项。** 修复当前门禁，明确源码身份和文档事实；任何确认的 blocker/high 必须修复并回归。
- **P1：框架主线。** 完成共享工具执行器、自定义编排恢复、共同契约与真实宿主验证。
- **P2：交付完善。** 接入体验、文档、版本兼容和基于实测的改进；涉及公开承诺的部分在发布前完成。
- **P3：条件扩展。** 生产平台、旧知识应用补全、更多业务与多 Agent 策略，按需求和证据立项。

设置三个独立结论，避免一个通过标志覆盖全部范围：

| 结论 | 必须具备的证据 |
| --- | --- |
| SDK 工程验收 | 当前源码冻结、声明范围内完整门禁、独立干净副本、构建/最小安装、审查与残余风险 |
| 两个真实应用接入验收 | 法律与电商均连接实际宿主身份/数据/接口；共用核心与契约，无业务专属核心分支 |
| 业务质量验收 | 冻结的真实模型、独立数据、明确评分与领域评审；质量、成本、时延和失败结果都有记录 |

如果电商暂时只有模拟宿主，结论必须写为“一个真实宿主 + 一个参考应用”。生产部署另设运行与安全验收，不由以上结论自动推导。

以下人日为单名熟悉代码的开发者的粗估，包含实现、测试和文档，不含等待宿主接口、评审人、模型资源的时间；执行前按设计结果重新估算。

| 编号 | 优先级 | 工作包 | 依赖 | 主要交付物 | 粗估 |
| --- | --- | --- | --- | --- | --- |
| R0 | P0 | 基线修复与事实校准 | 无 | 检查报告、差异说明、源码清单 | 1–2 人日 |
| R1 | P1 | F1c-2a 共享工具执行器 | R0 | ADR、执行器、ReAct 回归 | 4–7 人日 |

| R3 | P1 | 扩展共同契约与安装矩阵 | R0；写路径部分依赖 R2 | conformance 表、测试、安装证据 | 3–5 人日 |
| R4 | P1 | LexVault 真实只读宿主验证 | R0；复用现有只读 kernel | host adapter、可复现试点、对照报告 | 4–7 人日 |
| R5 | P1 | 电商实际宿主最小闭环 | R0；复用现有 ReAct 写路径 | 认证/商品/工单适配、闭环证据 | 5–8 人日 |

合计约 **30–52 人日**，是工作量估算而非交付日期。R4/R5 的只读或 ReAct 试点可以与 R1/R2 并行；不必等待自定义写路径才能开始验证真实宿主。最终业务评测必须绑定稳定候选：先执行 R8 的冻结与工程审查，再执行 R6 终评，最后汇总 R8 结论。代码变化后重新冻结并重跑适用门禁；已消费的封存集保留为历史结果，需重新终评时另建独立封存集。

## 4. 各工作包执行要求

### R0：先建立可信基线

**任务**

1. 保存当前源码文件列表与摘要，明确排除环境、缓存、生成报告和秘密；记录没有 Git 元数据的事实。
2. 修复已确认的 15 个格式问题，并检查全仓库正式格式/lint 范围。
3. 用明确的 Python 3.12、锁定依赖和测试采集命令生成 JUnit 与 nodeid 清单，解释 1116/1123 的差异。查明前在文档中保留“未核实”，不把旧数字当事实。
4. 更新当前状态入口，标明历史段落的适用日期与源码；校准 README、SDK_GUIDE 和路线图的版本/完成状态。
5. 建立本轮 findings 表，每项记录适用范围、严重程度、状态、责任角色和回归证据。
6. 为新候选验证选择独立输出目录；现有固定路径的脚本需要先适配，不能覆盖 10 月 17 日及更早冻结记录。同步 CI 的发布验证入口、版本、示例清单和 artifact 上传路径；当前 `release-candidate` 仍指向旧 `reports/next-candidate`。

**验收**

- format、lint、mypy、锁一致性及当前测试通过；测试总数从报告生成。
- 文档没有把旧候选数字、过期“未实现”描述套用到新源码。
- 可从 manifest 重建相同源码集合；缓存和报告不构成源码身份。
- CI 和本地验证使用同一当前候选入口；变更旧候选仍被拒绝，新尝试有独立证据，失败日志也保留。
- 如果恢复或建立 Git 管理，记录真实来源；不得补造历史提交。Git 的恢复方式不阻塞基于 manifest 的基线保存。

### R1：抽取共享工具执行器

**任务**

1. 绘制 ReAct 当前工具路径，标清参数校验、当前授权、策略、审批消费、调用准入、journal、重试、结果和 checkpoint 的顺序。
2. 编写 ADR：执行器接口、输入/输出、状态所有权、失败类型、事务边界、并发行为和兼容策略；先定义 R2 所需的挂起信号与持久编排契约，再开始抽取，避免后续返工。
3. 从 `AgentRuntime` 抽取已有工具执行机制，让 ReAct 先使用共享实现；覆盖原有行为后再让 kernel 接入。
4. 保留逻辑调用与物理尝试的区别：重试使用同一业务键，物理尝试消耗独立预算。
5. 统一事件与证据的归属，避免 kernel 与执行器重复记账、重复完成或漏记失败。

**验收**

- 原有工具、审批、journal、恢复、重试、deadline、Coding 和电商回归通过。
- 非法参数、拒绝策略、未授权动作在副作用发生前被拒绝。
- 已完成结果正确复用；结果未知的非幂等调用不自动重放。
- 注入“审批消费后、journal 前”“工具完成后、checkpoint 前”等故障，结果与既有恢复契约一致。
- 不复制第二套审批/journal 控制状态；R2 完成前保留 ADR 026 的自定义写路径限制。

### R2：定义并实现自定义编排挂起/恢复

**任务**

1. 定义可持久化的编排进度：编排版本、稳定节点 ID、节点输入摘要、完成证据引用、待审批动作、累计预算与未决副作用。当前 checkpoint 只保存消息、用量和工具证据，不能直接恢复任意 Python 协程；必须声明受支持的编排状态协议。
2. 明确恢复单元和重放规则；已完成节点复用持久结果，未完成节点按当前权限、策略和资源版本重新准入。
3. 接入 `Harness.approve/resume/inspect`，支持进程重建后的审批和恢复。
4. 定义 fan-out 时多个节点失败、取消、等待审批的收敛规则；预算原子准入、稳定调用 ID、证据顺序、checkpoint 和单运行写者约束必须确定。这些属于设计验证项，不是本次已确认的并发缺陷。
5. 为新旧持久格式制定版本与拒绝/迁移规则；没有迁移实现的旧状态不得静默按新语义执行。
6. 选一个最小自定义写流程验证；应用业务写入仍由宿主工具执行。

**验收**

- 重启后可还原待审批动作，批准精确绑定主体、资源、参数、版本和有效期。
- 改参数、换租户/主体、撤权、资源更新、过期批准、重复批准均不能产生越权写入。
- completed/claimed/started-readonly/started-idempotent/started-non-idempotent/缺失记录各有明确结果。
- 并行执行与恢复不会重复扣费、漏计使用量或重复产生业务结果。
- soft deadline 不被误写为正在执行的外部副作用已回滚。
- 覆盖同一 ReAct 故障窗口后才解除对应自定义写路径限制；不承诺任意外部系统的 exactly-once。

### R3：扩展共同契约与安装矩阵

**任务**

1. 将现有成功、trace、inspect、验证拒绝、错误绑定和缺资源子集扩展为完整适用矩阵。
2. 补权限撤销、策略 deny/approval、预算耗尽、模型协议违规、工具失败、取消/deadline、重建、删除及恢复。
3. 对自定义编排增加治理机制一致性测试；对真实应用按其能力执行相同契约。只读法律应用的写审批列可以标记“不适用”，不能用跳过伪装通过。
4. 保留核心导入边界测试，包括动态 import；三个 Coding 兼容 shim 与 SDK application shim 分别登记。
5. 验证基础 wheel、模型/Web/知识等实际声明的 extras、参考应用资源与干净安装。当前不存在的 `[legal]`/`[commerce]` extra 不写成可用命令。
6. 核对 `requires-python >=3.12,<3.14` 的支持声明：Python 3.12 为必测基线，补 Python 3.13 兼容检查；若暂不支持，先调整发行声明并说明兼容变化。

**验收**

- 每项矩阵都有用例、结果或明确的不适用理由；关键缺口不能仅用不同文件的零散测试概述代替。
- 新应用只新增 app/adapter 与契约实现，不在核心添加法律/电商专属分支。
- 基础安装不隐式依赖 FastAPI、知识平台或模型下载。
- 导入、工具顺序、组合结构摘要、API v1 兼容及构建资源检查通过。
- 至少验证一个可跨应用复用的能力，或记录领域能力不应强行共用的具体理由。

### R4：LexVault 真实只读宿主验证

**任务**

1. 与宿主明确认证主体、案件/页级授权、稳定版本、更新和撤回信号；现有离线 bundle 的访问范围不能代替宿主当前权限。
2. 以独立 Python 3.12 服务或进程为起点，消费授权导出或只读快照；接入宿主真实专家 DAG 与混合检索，保留其领域规则。已有词匹配原型用于回归，不作为真实业务 DAG 接入的完成证明。
3. 在当前应用上下文下验证检索、读页、引用、inspect 和历史访问；撤权与资料变更后必须有明确失效行为。
4. 形成版本化导出→执行→结果→证据的可重跑入口；记录源数据只读证明。
5. 先用开发题验证链路，再按现有 LexVault 子计划执行 8 题试点；结果满足进入条件后才扩大到 16 题及专业复核。
6. 记录回退路径和接入所需核心改动；如出现通用缺口，先修契约，不添加案件类型专属核心逻辑。
7. 显式设置并冻结严格逐引用原文模式；分别核对页身份、原文精确匹配和结论支持，记录允许的引用格式与拒绝行为。

**验收**

- 真实宿主身份与页权限生效，跨案/跨租户泄漏为 0；撤权后不能通过历史或 inspect 获取受限证据。
- 导出原文、文档/页身份、digest 和引用可追溯；精确引文校验失败不能报告成功。
- 试点对原宿主没有写入，停止试点服务后原路径仍能工作。
- 明确报告“来源存在/原文匹配”与“证据支持结论/法律正确”两个层次，后者由 R6 验收。
- 当前四题脚本运行作为历史链路证据保留，不计入真实模型终评。

**外部前提**：宿主接口契约、可使用案件材料及授权范围、测试身份、专业复核人。对外部 LexVault 仓库的改动需明确工作区范围后实施。

### R5：电商实际宿主最小闭环

**任务**

1. 选择一个明确宿主，接入其认证、商品/SKU、当前价格库存、知识版本和工单接口。
2. 复用 SessionService、RevisionStore 和现有 ReAct 写路径，完成“咨询→证据→澄清/转接→工单回执”。
3. 区分自然语言理解与确定性台账正确性；先记录真实模型开发集表现，再扩展开放式推荐。
4. 补足无商品证据时的可用转接流程：选择通用工单或明确限制路径并记录产品决定。
5. 工单同时具备业务 request_id 去重和框架逻辑调用去重；对超时采用结果查询/核对机制。
6. 以现有控制台为起点补最小操作与错误反馈；真实用户试点前替换演示身份，核对审批、来源失效和保留/删除流程。

**验收**

- 价格、库存、币种与时间均来自本次宿主结果；缺失或过期数据不被模型补造。
- 撤回知识和已失效来源不能继续被当作当前事实。
- 跨店铺访问为 0；未批准写入、重复工单和虚假完成为 0。
- “已接收/排队”与“工单已创建”按实际回执分别呈现。
- 用真实接口走通一次完整闭环并保留脱敏证据；只有模拟接口时，交付标签仍为参考应用。

**外部前提**：宿主身份和 API、测试商家/商品、可查询的工单回执、业务负责人。真实渠道外发、支付、退款和改价不纳入这个最小闭环。

### R6：真实模型与领域质量评测

**任务**

1. 固定模型标识、参数、预算、工具集合、数据版本与评分规则；确认允许使用的数据和模型环境。
2. 法律与电商各准备独立开发材料和标注；合成场景数与独立业务题数分开记录。
3. 对事实、引用支持、应澄清/转人工、专业结论设置人工复核；法律结论需要专业评审。
4. 记录真实 usage、失败、重试、p50/p95 时延及成本；无法获取的指标标为未知，启发式估算不冒充真实 token 上界或账单。
5. 需要比较多 Agent、ReAct/Plan-Execute 或其他框架时，先固定任务、模型、资源和评分口径；仅在质量收益与成本可接受时引入复杂编排。
6. 封存集只用于正式终评：在读取前写不可覆盖的 Targets 声明并按既有消费规则执行。调参使用开发集；失败结果也保留。
7. 法律同题对照固定相同问题与可用证据范围，预先约定不劣于基线的判据，尽可能采用盲评；用结果形成保留原生、只吸收能力或迁移的 ADR，并单独决定 LangGraph 的处置。

**建议门槛**

沿用 [quality-targets.json](../evals/business/quality-targets.json) 的待验证提案，正式终评前由业务与评审负责人确定分母、适用领域和时延/成本限额：

| 指标 | 提案门槛 |
| --- | --- |
| 精确引用率 | 100% |
| 可核验事实正确率 | ≥95% |
| 应转人工场景的正确处理率 | ≥95% |
| 跨范围泄漏、未批准副作用、重复副作用、虚假完成 | 均为 0 |
| 证据支持结论与法律质量 | 领域量表、专业评审和分歧记录；原文匹配不能替代 |
| 成本和时延 | 运行前确定预算与阈值；逐类报告，不只给总体均值 |

**验收**

- 开发报告与终评报告清楚分开，报告绑定真实模型、源码、数据、预算和评分版本。
- 安全硬门槛失败即停止资格判定并进入修复，不用总平均分抵消。
- 没有真实模型或必要专业评审时，业务资格保持未通过/未测。
- 现有 40 法律/80 电商 keyless 契约和 60 条合成封存夹具不自动升级为真实业务质量证据。

### R7：文档、版本与独立接入验证

**任务**

1. 重写 README 的主叙事，以 SDK、能力组合、两条执行路径和应用接入为主；保留可选知识/Coding 平台说明。
2. 校准 SDK_GUIDE 的发行版本、兼容路径、错误语义和安装命令，补一份最小自定义编排及真实宿主适配示例。
3. 发布 API/事件/checkpoint/编排状态的版本策略；明确何时升级应用版本、何时拒绝旧状态。
4. 登记三个 Coding shim 与 `sdk/application.py` shim 的 API v2 移除条件，API v1 阶段继续兼容。
5. 让未参与核心实现的接入者按指南完成一个 toy app，再记录真实宿主接入的耗时、疑点和所需核心改动。
6. 逐项校对公开说明、量化结果和简历材料；每个数字链接到适用候选证据，上游借鉴保留归属。

**验收**

- 指南命令在干净环境可运行，没有引用尚未提供的 extra 或 API。
- 接入者可通过公共接口完成装配，并提供实际接入记录；不能用作者自报替代。
- 当前事实、计划、历史结果有明确标识；测试总数与报告一致。
- 不宣称通用框架优势、生产可用或法律正确性，除非对应证据已完成。

### R8：冻结候选、全面审查、干净复验

**执行顺序**

1. 固定本轮发布范围和精确源码清单；记录工具链、锁文件、构建输入、评测配置及排除规则。
2. 在独立报告目录运行源码侧完整门禁，保存 stdout/stderr、JUnit、覆盖率和结构化结果。
3. 审查架构、正确性、测试、安全边界、依赖、文档和公开履历承诺；所有发现都分类。
4. 修复 blocker/high，确认的行为缺陷必须增加回归测试；源码变化后生成新候选身份，旧尝试保留。
5. 从相同冻结清单创建干净副本和新 Python 3.12 环境，重跑完整适用门禁并核对源码未变。
6. 输出工程/宿主接入/业务质量三项独立结论，列明残余风险、责任角色和重新审查触发条件。

**最少门禁集合**

- 全仓库 format/lint、mypy，以及可选对照实现的类型检查。
- 全量测试零失败/错误；意外跳过不得算作通过；纯分支覆盖率 **≥85%**，独立于 combined coverage。
- keyless control、Agent dev、40 法律/80 电商开发契约、安全场景，以及本轮新增的恢复/conformance 用例。
- 当前声明范围内的 RAG、Reviewer、宿主集成与真实模型评测；未纳入范围的历史平台结果明确排除。
- 锁一致性、环境依赖检查、核心及实际发行 extras 漏洞审计；历史可选 NLTK 例外重新核查适用性。
- wheel/sdist 文件清单与摘要、资源完整性、最小安装和示例运行；秘密、私有案件与封存正文不进入发行包。
- 对照框架适配如保留在发布范围，复验其固定版本组合场景；33 项共同宿主集成不能替代完整原生故障对照。
- 源码/干净副本/构建产物/报告身份一致，运行结束后再次核对候选摘要。

**证据目录建议**

为本轮配置独立目录，例如 `reports/framework-next/`，包含 `source.json`、不可覆盖的 `verification/runs/<attempt>/`、摘要、findings 和验收报告。该目录是拟定输出；本计划不代表它已创建。优先扩展已有验证驱动的输出路径能力，避免复制整套驱动或覆盖历史证据。

## 6. 推荐执行顺序

```text
R0 基线修复与事实校准
 ├─ R1 共享工具执行器 → R2 自定义审批/恢复
 ├─ R3 只读契约/安装 → 补写路径契约
 ├─ R4 LexVault 宿主 / R5 电商宿主 → R6 开发评测
 └─ R7 文档/版本/接入记录（持续）
                 ↓ 实现、配置及评测方案稳定
       R8 冻结 → 工程审查/修复/新候选干净复验
                 ↓
       R6 正式终评 → R8 汇总三项独立资格结论
```

| 批次 | 推荐交付 | 阶段决策 |
| --- | --- | --- |
| 第一批 | R0；R1 ADR；R4/R5 接口与测试数据清单；R6 开发评分方案 | 当前基线可继续开发，外部依赖有负责人 |
| 第二批 | R1；R3 只读矩阵；R4/R5 首条真实宿主链路 | 共享执行器稳定，真实接入无领域核心分支 |
| 第三批 | R2；完整适用 conformance；R4/R5 异常与撤权闭环 | 自定义写路径具备明确恢复证据 |
| 第四批 | R7 定稿；R8 冻结及工程审查/复验；R6 正式评测；R8 汇总结论 | 分别给出工程、宿主、业务资格结论 |

若外部宿主或评审条件未具备，可先完成并验收明确缩小范围的 SDK 工程候选；真实宿主/业务项目保持待完成状态。任何阶段发现 blocker/high，优先修复并重做受影响门禁。
