## 1. 目标与交付等级

### 1.1 产品定位

> 基于 ForgeHarness 的电商咨询与人工服务工作台：为小型商家提供有商品与知识来源支持的智能咨询；
> 无法可靠回答时收集必要信息并转交人工，支持独立审批、工单处理、运行记录与故障恢复。

首版不解释框架名词，只交付业务结果。三个角色各自的问题与应得结果：

| 角色 | 实际问题 | 应交付结果 |
| --- | --- | --- |
| 咨询用户 | 不知道商品差异、适用条件、售后规则 | 有依据的回答，或明确的补充信息要求 |
| 客服 | 接手时要重新询问，缺上下文 | 带摘要、来源与待确认问题的工单 |
| 管理员 | 不清楚模型是否乱答、调用是否失控、故障后是否重复执行 | 可查询的状态、用量、审批与处理证据 |

### 1.2 三个交付等级与停止点

| 等级 | 交付目标 | 使用者 | 完成后的表述上限 |
| --- | --- | --- | --- |
| A 展示版 | 完整主链路、真实模型、真实登录、在线部署、可重复演示 | 本人、少量邀请用户 | “已部署的 Agent 应用项目” |
| B 受控试用版 | 多真实账户、反馈闭环、成本与质量测量、恢复演练 | 2–5 位邀请试用者 | “经小范围真实用户试用的 Agent 应用” |
| C 商业 SaaS | 多组织、配额、套餐与运营 | 外部客户 | 按实际部署与运营结果表述 |

本计划把 **A+B 作为完整范围**，C 为条件触发（见第 16 节）。A 完成即可交付体验；
B 的价值在于把“能跑”变成“有证据”。

## 5. 身份、权限与用户隔离

多人上线前的最高优先级。实现落点：`src/forgeharness/applications/commerce/identity.py`
（存储与权限）与 `identity_http.py`（认证路由与依赖注入）。

### 5.1 实体

| 实体 | 键 | 最小内容 |
| --- | --- | --- |
| 用户 | `users.id` | 规范化邮箱、显示名、状态、scrypt 盐与摘要 |
| 工作空间 | `workspaces.id` | 名称、状态 |
| 成员关系 | `(workspace_id, user_id, role)` | 启用状态、创建时间 |
| 邀请 | `invitations.token_hash` | 邮箱、角色、邀请人、过期、接受、撤销 |
| 浏览器会话 | `web_sessions.token_hash` | 用户、工作空间、CSRF、签发/过期/撤销 |
| 审批会话 | `approval_sessions.token_hash` | 审批人、工作空间、短 TTL |
| 会话绑定 | `(workspace_id, session_id)` | owner 用户、创建、关闭 |
| 审计 | `audit.seq` | 操作者、动作、对象、结果、时间 |

令牌只存 SHA-256 摘要；密码用 `hashlib.scrypt` 加盐，比较用 `hmac.compare_digest`。

### 5.2 角色 → 权限（代码常量，非文档约定）

| 角色 | 权限 |
| --- | --- |
| `customer` | `consult`、`ticket:read_own` |
| `support` | `ticket:read_scope`、`ticket:claim`、`ticket:resolve` |
| `supervisor` | `ticket:read_scope`、`approval:decide` |
| `editor` | `knowledge:read`、`knowledge:draft` |
| `publisher` | `knowledge:read`、`knowledge:review`、`knowledge:publish` |
| `admin` | `member:manage`、`quota:manage`、`knowledge:read` |

`admin` **不含** `approval:decide`，也不含 `consult`：管理员不能借角色自动绕过业务审批，
该限制由权限表固定，而不是靠流程约定。

### 5.3 认证与令牌

- 登录：`POST /identity/login`，成功签发 `fh_identity` Cookie：`HttpOnly`、`SameSite=Lax`、
  部署启用 HTTPS 时 `Secure`、`Path=/`、8 小时绝对过期，不做滑动续期。
- CSRF：所有非安全方法必须带 `X-CSRF-Token`，与服务器端会话记录比对；
  缺失或不匹配一律拒绝，不做“宽容模式”。
- 退出：`POST /identity/logout` 撤销服务端记录，Cookie 失效不依赖浏览器删除。
- 登录节流：同一邮箱在时间窗内的失败次数超限即拒绝，失败计数与成功登录都写审计。
- 用户枚举：未知邮箱、错误密码、被禁用账户返回同一错误文案。

### 5.4 审批独立通道

审批不能与业务会话共用身份。审批人先用 `POST /identity/approval` 用自己的凭据换一个
**短时审批令牌**（10 分钟、单次使用范围、可撤销），业务请求通过 `X-Approval-Token`
携带。服务端每次审批都重新读该用户的当前状态与角色，并强制：

1. `actor.id` 必须与任务 owner 不同（SDK `can_approve` 同款约束，双层校验）；
2. 审批人必须持有 `approval:decide`；
3. 审批人与 owner 的 `scope`（工作空间与资源集合）必须一致；
4. 审批人身份不从请求体、路径或模型文本读取。

### 5.5 对象级授权

对象 ID 不是授权凭证。每次访问都必须重新核验：

| 对象 | 核验 |
| --- | --- |
| 会话 | `consultation_sessions` 绑定的 owner 与当前 `actor.id` 一致；SDK 侧再校验 `session.actor_id` |
| 工单 | 同租户 + (`requester_id` = 自己 且 `ticket:read_own`) 或 `ticket:read_scope` |
| 知识资源 | `scope.resources` 含该 `faq:`/`product:` 且角色具备读写权限 |
| 审批 | 见 5.4，四条全部满足 |

`scope.resources` 由服务端按工作空间计算，不接受客户端提交的资源列表。

### 5.6 越权测试矩阵（W1 出口）

| 用例 | 期望 |
| --- | --- |
| A 访问 B 的会话 ID | 403/404，且不泄露存在性 |
| A 用 B 的会话 ID 提交问题 | 拒绝，B 的会话状态不变 |
| 普通用户调用审批接口 | 403 |
| 审批人审批自己的任务 | 拒绝 |
| 管理员审批业务操作 | 拒绝（无 `approval:decide`） |
| 禁用审批人复用旧令牌 | 拒绝 |
| 撤销成员后继续读取 | 拒绝 |
| 重放过期 Cookie | 401/403 |
| 跨租户读取工单/来源 | 拒绝 |
| 请求体伪造 `actor`/`roles`/`tenant` | 无效（`extra="forbid"` + 服务端取值） |

规模建议（非指标）：20–50 个商品、30–80 条 FAQ、少量带版本的售后/配送说明。

| 来源层 | 允许用途 | 报告表述 |

## 7. 真实模型接入（两步）

**第一步：模型理解与选择，事实由结构化结果呈现。** 模型负责理解问题、选择允许的工具、
选相关商品、判断是否澄清；系统负责参数校验、权限与审批、真实台账读取与确定性展示。
验收器仍要求最终内容与工具结果一致，先保住可验证性。

**第二步：允许自然语言总结，另建输出验证。** 输出结构：

| 字段 | 校验 |
| --- | --- |
| `answer` | 结构合法、长度上限 |
| `citations` | 来源存在、当前可访问、版本有效 |
| `products` | 商品在授权范围内 |
| `needs_info` | 澄清点非空且具体 |
| `handoff` | 建议转人工时附摘要 |
| `receipts` | 引用的操作回执真实存在 |

结构验证与来源验证不能替代语义评估；后者需要标注数据与人工抽查。

接入任务：固定首个模型与参数；配置步数/工具调用/token 预算；超时、最大输出、历史窗口；
记录模型与提示词版本；核对实际发送输入与 trace 一致；处理拒答、格式错误、超时、用量未知；
重试计入成本；为新模型建立独立回归。

回归场景（全部必须拒绝或如实降级）：无工具直接乱答、非法 SKU、超范围资源、伪造来源、
要求绕过审批、资料内提示注入、模型超时、用量缺失、格式错误、未创建工单却宣称成功。

## 8. 主链路、对象与状态

三个对象，三个状态，不合并：

| 对象 | 含义 | 状态 |
| --- | --- | --- |
| 会话 | 一段持续交流 | 活动 / 已关闭 / 已删除 |
| 运行轮次 | 一次问题处理或操作 | 已接收 / 执行中 / 待审批 / 已完成 / 失败 / 预算耗尽 / 待核对 / 已取消 |
| 工单 | 客服事项 | `open → assigned → resolved`、`open → cancelled`（现有四转移为基线） |

五条演示路径与验收点：

1. **正常咨询**：登录 → 新建会话 → 提问 → 工具取数 → 有来源回答 → 追问重新取数。
   验收：价格库存来自当前工具结果；来源可打开；追问不复用旧库存；用户不需填 SKU/会话 ID。
2. **无证据转人工**：提问 → 证据不足 → 建议转人工 → 用户确认摘要 → 独立审批 → 工单 → 查进度。
   验收：“建议”“待审批”“已创建”三态可区分；未明确请求不产生写入；创建需可信回执。
3. **客服处理**：客服登录 → 授权工单 → 领取 → 看上下文 → 处理 → 记录 → 解决。
   验收：两人同时领取只有一人成功；普通用户不能执行客服操作；用户能看到处理结果；
   不把“模型轮次成功”显示成“客服已解决”。
4. **知识更新**：编辑 → 提交审核 → 独立审核 → 发布 → 新咨询用新版本 → 撤回后停止使用。
   验收：草稿不进正式回答；权限清晰；撤回后历史访问遵循既有授权契约。
5. **异常恢复**：发起 → 断网/重启 → 重新登录 → 查询原请求 → 显示真实状态 → 允许时续跑。
   验收：断网不等于失败；刷新不产生第二次业务请求；结果未知的写入先查回执。

## 9. 工单闭环

在现有 `tickets` 表上增列（W5）：`requester_id`、`assignee_id`、`resolution`、
`version`（乐观锁）、`updated_at`；保留 `UNIQUE(tenant, request_id)` 作为业务幂等键。

| 操作 | 规则 |
| --- | --- |
| 领取 | `BEGIN IMMEDIATE` 内条件更新 `assignee_id IS NULL AND status='open'`；并发只允许一次成功 |
| 解决 | 仅 assignee 或 `ticket:resolve`；写 `resolution`、操作者、时间；状态一次前进 |
| 取消 | 仅 requester 且状态为 `open` |
| 读取 | 见 5.5；越权返回与“不存在”相同的响应 |
| 外部同步 | 适配器需支持创建、按业务键查询、状态查询、超时后核对；无去重能力时交人工核对 |

禁止：HTTP 路由绕过审批直接写工单；用“模型说成功”代替台账回执；
恢复旧备份后对外部已完成写入重复执行。

## 10. 请求幂等与断线恢复

1. 用户发起新操作时生成 `request_id`，在操作结束前所有重试复用它。
2. 提交期间禁用重复触发；浏览器只保存请求标识与查询位置，不保存问题草稿（除非确认数据敏感性）。
3. 收到轮次 ID 后记录查询位置；网络异常先查原任务，再决定重试。
4. 服务端按 `request_id` 返回已有轮次（现有 `SessionService.submit` 已支持）。
5. 只有用户明确开始新操作时才产生新标识。

A 级采用同步请求 + 持久状态查询；真实模型耗时超出 HTTP/代理适用范围时，B 级引入后台任务，
要求：持久入队记录、确定 owner、崩溃后状态核对、执行前重查权限、队列状态与 Harness 状态单向映射
（队列负责调度，Harness 负责执行事实，不建第二套完成状态）。

取消需单独设计：明确能停止哪些后续操作、在途调用如何处理、已发生副作用如何保留。

| 层 | 职责 |
| --- | --- |
| 浏览器前端 | 咨询、工单、审批、管理、用量 |

停止接收新任务与正常退出的流程。

（模型与外部服务最近一次检查）。高频探针不得触发付费模型调用。

## 13. 备份、恢复、保留与升级

备份清单：应用版本、SDK wheel 摘要、DB schema、配置身份、状态绝对路径、
备份时间与文件摘要、未完成运行与待审批事项、外部回执引用、恢复步骤。
文件摘要可检测变化，但需与备份分离存放；随备份保存的摘要不是独立可信证明。

四种演练：普通重启（历史一致）、待审批时重启（仍待审批、无写入）、停机备份同路径恢复
（任务/审批/trace/工单对应一致）、外部写入后恢复较旧状态（查回执，避免重复执行）。
记录实际耗时与恢复点，由业务目标判断是否足够。

保留策略覆盖：会话文本、模型输入输出、工单与处理记录、资料版本、审计、用量、备份、
已删除对象的防重放标识。删除必须同时处理在线存储、日志与备份，并说明恢复后如何避免重新暴露。

升级规则：新任务用新版本；旧任务保持原绑定或走已验收迁移；旧版本不得接管无法识别的新状态；
先在隔离环境验证再升级试用实例；保留可恢复的原状态与发行物。

## 14. 测试与评估

| 层级 | 重点 |
| --- | --- |
| 单元 | 权限判定、参数校验、状态流转、预算 |
| 集成 | 认证→会话、审批→工具、工单→台账 |
| 浏览器 E2E | 登录、咨询、来源、审批、工单、刷新 |
| 故障 | 超时、重启、重复请求、撤权、结果未知 |
| 模型质量 | 事实、引用、澄清、工具选择 |
| 人工试用 | 能否独立完成、卡在哪里、需要多少帮助 |

固定 15 条 E2E 场景（均必须自动可跑）：登录完成有来源问答；两会话隔离；无证据不编造；
确认后进入待审批；普通用户不能自批；审批后只建一张工单；重复点击/断网不重复建单；
客服领取并解决；用户只看自己的工单；撤回后拒绝；撤权后拒绝；超时状态如实；
预算耗尽停止调用；待审批期间重启可恢复；恢复旧备份不重复执行已完成写入。

真实模型评估：开发集 40–60 题，独立终评集 60–100 题；部分题重复运行看稳定性，
重复不计为新题；安全边界单列，不与正确率混合平均。

任务族：单商品事实、多商品比较、售后 FAQ、多轮追问、描述不清、无证据、资料冲突/失效、
人工转接、权限与提示注入、超时与重复提交。

| 指标 | 门槛提案 |
| --- | --- |
| 事实正确率 | ≥95% |
| 引用有效率 | 100% |
| 澄清/转人工正确率 | ≥95% |
| 任务完成率 | 按任务族报告 |
| 未授权读写 / 重复副作用 / 虚假完成 | 0 |
| 时延 | 分族 p50/p95，含排队与失败 |
| 费用 | 成功、失败、重试、未知用量分开记 |

门槛须在正式评估前冻结；小样本全过不代表总体风险为零。终评规则：冻结模型/提示词/工具/数据/评分；
先定通过条件再看结果；保留全部失败；据终评改动后须用新的独立集合复评；
不把合成契约分数写成真实业务准确率。

## 15. 试用与反馈

2–5 位非开发参与者，覆盖咨询用户、模拟客服、资料维护/审批人。

任务卡：找到适合某需求的商品；比较两个商品；提交无法回答的问题；查询自己的工单；

（脱敏）截图、修复方式、是否复验。
