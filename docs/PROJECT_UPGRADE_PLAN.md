## 1. 目标与定位

将 ForgeHarness 提升为一个可以完整演示、解释设计取舍、复现评测结果的**研发 Agent 执行与知识平台**，重点服务 Agent 应用工程与 Agent 基础设施方向的项目展示和技术面试。

核心交付场景是：开发者提交问题，系统检索项目知识、定位代码，在明确授权的工作区内修改、验证并交付补丁；全过程可以查看依据、预算、审批和失败原因，中断后能按确定的规则处理。

执行假设：单人开发，每周投入 20–25 小时；首轮目标为本机或受控单租户环境，继续使用 Python 3.12、uv 和框架独立的核心运行时。建议安排约 10 周，工程估算 156–200 小时，另留约 20% 缓冲，总计约 187–240 小时。模型服务、数据标注或阻断问题造成的等待不计入净开发时间。

成功标准包含三部分：

1. **工程可交付**：三条核心工作流可重复运行，明确成功、失败、等待审批和结果不确定的边界。
2. **效果有证据**：真实任务评测、失败案例和版本绑定的报告支撑对外结论。
3. **个人能解释**：能独立讲清运行时、检索、恢复和成本的设计，并实际完成故障诊断与面试演练。

本计划承接 [NEXT_PHASE_PLAN.md](NEXT_PHASE_PLAN.md)，用 U0–U6 标识后续工作，避免与已有 M8–M10 混淆。现有完成项优先复用；正式实施时逐项更新 [STATUS.md](STATUS.md)，本计划不替代实现状态记录。

- **真实业务质量证据不足。** 现有 RAG 评测以受控 fixture 为主，引用来源正确不等于引用支持答案中的每项断言。

历史评测中一个值得保留的结论：在一个本地 9B 模型、自建 14 题 holdout、每题每策略 5 次采样的实验里，ReAct 为 11/14，Plan-Execute 为 10/14；后者中位步数、输入 token 和延迟更高。它支持“先保留简单基线，再证明复杂策略收益”的项目方法，不能外推为普遍优劣。详见 [M8C_HOLDOUT_REPORT.md](M8C_HOLDOUT_REPORT.md)；这些是历史报告结果，不是本次实测。

## 4. 三条目标工作流

### A. 有依据的研发知识问答

用户提问“这个模块为什么这样设计”，并继续追问“刚才提到的方案有哪些限制”。系统结合项目文档、代码位置和会话上下文回答，展示引用；资料不足、互相冲突或版本不匹配时明确说明。

交付物：持久化回答、来源位置、检索过程、使用的文档版本、上下文选择记录、token 与耗时。

### B. 受控的 Issue 修复与补丁交付

用户选择授权仓库并描述问题。系统检索知识、定位文件，展示拟修改内容与风险；获得对具体动作的审批后写入，执行固定验证命令、读取差异，导出补丁与验证报告。

交付物：`patch.diff`、结构化验收结果、最终工作区版本/摘要、测试记录、修改清单、未验证项和完整运行标识。修改后必须重新验证，测试通过不能证明全部需求正确。

### C. 中断恢复与失败诊断

在等待审批、工具执行前、执行后未落 checkpoint 等位置中断。重启后能找回任务、显示当前状态、复用已完成结果；无法确认副作用时停止自动执行，明确要求人工核对。

交付物：恢复决策记录、调用日志、可读时间线，以及可复现的故障案例。自动恢复与人工处理必须在界面和报告中明确区分。

## 5. 里程碑与验收

### U0：核对状态与冻结基线

优先级 P0；预计 12–16 小时；依赖：无。

工作：

1. 建立能力清单，将项目声明映射到实现、测试、报告、版本和限制；每项标注已实现、已验证、待验证或计划中。
2. 清理 `STATUS.md` 的冲突，给旧报告补充历史适用范围；依据当前实现复核审计发现，不能仅凭代码存在关闭 High 问题。
3. 确认源码来源与 Git 历史。若当前只是导出副本，先保留文件摘要和来源说明，再在可追溯的仓库中实施；不能编造旧 commit 或声称旧报告已验证当前副本。
4. 在已固定的依赖环境建立本轮质量基线，记录真实失败；不覆盖原始历史报告。

验收：所有对外能力和数字有可定位依据；当前状态无相互矛盾的完成声明；形成唯一候选源码身份；列出本轮发布阻断项。

交付：`docs/CAPABILITY_MATRIX.md`、修订后的状态文档、独立基线记录。上述新文件均为计划产物。

### U1：统一会话上下文与运行生命周期

优先级 P0；预计 28–36 小时；依赖：U0。

工作：

1. 为 chat、knowledge、memory command、coding 建立共同的运行身份、开始/结束/失败记录和查询契约，保留各类型独有状态。
2. 复用上下文编译思路，统一处理当前问题、历史消息、检索证据、审核记忆和附件的预算与优先级；避免重复加入当前用户消息。
3. 持久化会话摘要、引用和关联任务；支持跨轮指代，明确会话摘要只是信息，不能成为授权依据。
4. 保存模型输入构成与来源。原始材料留在受控本地存储；分享包只包含许可公开或脱敏内容，不能为追踪完整性暴露秘密。
5. 增加运行详情视图：状态、引用、模型调用、上下文预算、失败原因和待处理动作。

验收：四类工作流均可在重启后查询真实运行结果；错误和取消路径有记录；固定用例中的上下文不超预算；跨会话读取隔离、附件绑定、记忆撤销和连续追问均有端到端证据。

落点：`knowledge/conversation.py`、`knowledge/runs.py`、`context/`、`api.py`、`web.py`。

### U2：完成本地审批与恢复闭环

优先级 P0；预计 32–40 小时；依赖：U0，运行展示依赖 U1。

工作：

1. 先写 ADR，明确 checkpoint、invocation journal、approval ledger 各自的事实所有权，以及审批消费和调用创建之间的崩溃窗口。
2. 在已有接口下引入持久审批实现，保持任务、工具、规范化参数、工作区身份、有效期和一次性消费绑定。
3. 使 API 能重建必要的运行对象与等待审批动作；恢复后重新验证工作区和动作指纹。
4. 列出 missing / claimed / started / completed / failed / indeterminate × 三类副作用的恢复矩阵。只实现能够证明安全的继续执行路径，其他状态明确停止。
5. 完成结果复用时补回模型可见 observation，避免“工具不重复执行，但模型不知道它已完成”。
6. 对 soft deadline、重试、预算和恢复后的计时采用明确版本化语义；不把 admission deadline 描述成硬墙钟上限。

验收：

- 审批等待期间重启后可继续；已消费、过期、参数或工作区不匹配的授权均被拒绝。
- 两个竞争请求不能重复消费同一授权，不能重复取得同一逻辑调用的执行资格。
- 完成的结果不会再次产生副作用；不确定的非幂等调用不会自动重放。
- 安全支持的恢复路径能到达明确终态；暂不支持的路径显示具体原因。
- 故障注入覆盖审批提交、审批消费、调用 started、工具完成、journal 完成、checkpoint 保存之间的关键窗口。

交付：恢复 ADR、状态矩阵、回归测试、故障演练报告和可演示的重启流程。范围仍是本地单进程恢复，不延伸为多 Worker 故障接管或任意副作用 exactly-once。

### U3：交付真实研发任务与业务 RAG

优先级 P1；预计 28–36 小时；依赖：U1、U2。

工作：

1. 选 2–3 个许可清晰、可本地运行的示例仓库，覆盖代码、设计文档、Issue、配置和版本差异；记录来源和使用许可。
2. 把知识结果以带来源的上下文交给修复任务，打通知识问答、定位、审批、修改、验证与补丁导出。
3. 强化验收证据的时序关联：测试结果绑定到对应工作区内容；最后一次修改后的测试才可支持最终交付。可依据任务类型扩展验收条件，但不把模型自述当成通过依据。
4. 为“无证据”“资料冲突”“过时版本”“来源存在但不支持结论”准备真实 RAG 案例。
5. 围绕研发知识问答、Issue 修复、失败分析整理少量版本化 Skills；复用已有 MCP 通道演示一个只读工具即可。
6. 展示模型等待、执行测试、人工审批和恢复所耗时间，收集使用者真正需要查看的证据。

验收：三条目标工作流均有可运行样例；修改后的验证失效规则有回归用例；导出的补丁可在相同基线应用并验证；知识答案可追溯到具体片段，缺证据时不会伪造引用。

交付：`examples/` 下三个完整演示、补丁交付格式、真实语料与任务清单、用户操作说明。

### U4：形成真实效果与成本证据

优先级 P1；预计 24–32 小时，模型运行时间另计；依赖：U3，评测设计从 U0 开始。

建议数据规模：

| 数据集 | 起始规模与划分 | 关注点 |
| --- | --- | --- |
| 研发 RAG | 60 题：40 dev + 20 新 holdout | 可回答、缺资料、冲突/过期信息、连续追问、引用支持 |
| 仓库任务 | 24 题：16 dev + 8 新 holdout | 定位修复、跨文件修改、配置问题、失败恢复 |
| 确定性控制集 | 复用已有集并补本轮边界案例 | 越权、审批、预算、重试、副作用、恢复状态 |

同源文档、相似 Issue 和模板变体按组划分，避免近重复跨 split。已运行且已被分析的旧 holdout 保留为历史终评；若用其错误指导新实现，后续只能将其作为回归集，不能继续称为未知测试集。

比较顺序：先比较基础检索与混合检索/重排，再比较上下文策略；编排复用已有 ReAct 与 Plan-Execute 对照。每轮只改变一个因素，固定源码、模型、配置、数据版本、运行环境和预算。

真实模型正式运行至少每题 3 次；按任务报告成功次数及总体分布。重复采样不增加独立题目数量。保留 `equal` 与 `natural` 两种预算视角，并记录预算是否实际生效。模型质量、运行时契约错误、基础设施错误分别计数。

| 指标 | 统计方式 / 预设目标 |
| --- | --- |
| 控制边界 | 冻结控制集全部通过；出现越权、重复副作用、错误授权或伪成功即阻断发布 |
| Coding 任务成功率 | 测试 + 任务验收器判断；首轮建议质量目标 ≥70%，属于待验证目标 |
| RAG 断言支持率 | 将回答拆成断言，由人工标注引用是否支持；建议目标 ≥90% |
| 应拒答题正确率 | 对标注为无充分证据的问题统计；建议目标 ≥95%，披露样本数 |
| 效率 | Steps、Logical Calls、Attempts、输入/输出 Token、P50/P95 延迟、人工审核时间 |
| 恢复 | 按故障窗口分别报告恢复完成率、安全停止率、人工处理率，不能将安全停止混算成任务成功 |

这些阈值在 dev 基线完成后、holdout 开放前定稿。真实结果未达标则保留候选状态并记录原因；因结果不佳不能事后删题或放宽标准。若需要根据终评继续优化，应准备新的未见终评集。

引用评估的主证据由人工标注产生。模型评委可辅助筛查，但不能单独证明语义正确；无法获得第二标注者时披露单人标注局限。冷/热启动、硬件、并发和模型服务状态随延迟报告一起保存。本地 token 不折算 API 费用。

多 Agent 作为可选实验：最多增加一个只读 Reviewer，与单 Agent 共享总预算；只有预注册的质量收益和成本条件在新数据上得到支持才考虑默认启用，零收益或负收益结果同样保留。

### U5：整理产品演示与个人面试材料

优先级 P1；预计 16–20 小时；依赖：U3、U4；个人学习贯穿全程。

交付：

- **3 分钟讲解**：服务谁、解决什么问题、个人完成了什么、目前的验证边界。
- **10 分钟演示**：知识追问 → 修复建议 → 明确审批 → 验证与补丁 → 一次失败/恢复记录。
- **30 分钟深挖**：状态所有权、审批消费、崩溃窗口、上下文预算、RAG 评测、编排成本六个专题。
- **6 张图**：总体架构、状态机、工具调用、审批恢复时序、RAG 链路、评测与交付流程。
- **20 道高频问题详答**：每题包含 60–120 秒讲解、源码证据、一个反例和设计取舍。
- **3 次真实模拟面试**：基础/原理、架构追问、业务和故障诊断各一次；保存实际反馈和改进记录。材料生成不能替代练习完成。

重点准备的问题包括：为什么自研 Harness；为什么引用有效不等于回答正确；审批为何不能只写进 Prompt；工具结果与 checkpoint 不一致时谁说了算；为什么不盲目重试；为什么 Plan-Execute 不默认优于 ReAct；模型更强后哪些工程边界仍然需要。

个人验收：不依赖生成的答案独立讲解关键链路，现场根据 Trace 定位一个失败，说明一个功能为何保留为默认关闭。简历明确个人设计、亲自验证和 AI 辅助完成的范围。

### U6：冻结候选、完整审计与发布判定

优先级 P0；预计 16–20 小时，缺陷修复使用缓冲；依赖：U0–U5。

按 AGENTS.md 的完成规则执行：冻结候选 → 全量质量与评测门禁 → 架构/正确性/测试/安全/依赖/文档/简历声明审查 → 修复 blocker/high 并补回归 → 再冻结 → 从干净 checkout 等价环境重跑 → 写明残余风险和最终边界。

既有离线检查入口为 `make gate`、框架检查及 `make review` / `forge review`；它们不能替代真实模型、RAG 语义质量、重启演练和产品工作流验证。按依赖 profile 准备环境，每份结果单独记录源码身份与配置。需要 Git 的冻结脚本必须先解决 U0 的目录来源问题。

历史开放项 FH-015/016/017 逐项复核。只完成本计划的局部演示不能直接关闭完整增强版审计要求：包括真实模型资格、冻结集成证据、Worker 在途故障、元数据存储边界等。完成剩余要求或保留 HOLD；缩小发布范围必须明确标注为新的较窄候选，不能追认整个旧计划已完成。

最终交付：一份可复现操作说明、一套绑定源码的证据清单、一份发布/不发布判定、一份已实现与未实现边界、一份可据实使用的简历项目描述。

## 7. 业务价值如何验证

选择小规模研发使用场景，记录“读懂设计并找到文件”“修复已知缺陷”“判断失败任务是否可以恢复”等任务的总耗时、模型等待、人工操作与审核时间、重做次数、结果是否可用。

可用 8 组难度接近但内容不同的任务做人工流程与辅助流程比较，交错顺序，降低先做一次带来的熟悉效应。只有自己参与时，结论标注为单人试用；不写成团队生产效率提升。使用者评价重点是：能否找到证据、能否判断应该批准什么、出错后是否知道下一步。

首轮的价值论证以可检查的交付物和时间记录为准。未来若真正服务多用户团队，再根据身份、租户、数据隔离、执行沙箱和运维需求单独制定平台化方案。

## 8. 技术范围与风险取舍

| 项目 | 本轮处理方式 | 原因 |
| --- | --- | --- |
| LangChain/LangGraph | 保留适配与对照，核心运行时保持独立 | 便于展示工程取舍，也遵守项目不变量 |
| GraphRAG | 先记录普通检索失败类型，需要关系推理时再试验 | 当前首要缺口是语义质量证据与业务串联 |
| 微调/标注平台 | 学习原理，暂不建设训练链路 | 需要独立数据、算力与评测目标 |
| 多 Agent | 可选只读 Reviewer 对照，默认策略由证据决定 | 控制成本与故障复杂度 |
| 多租户/K8s/高可用 | 后续独立计划 | 当前产品与验证范围是本地/受控单租户 |
| OS 级隔离 | 明确后续执行安全专题 | 路径检查与审批不能等同 OS 沙箱；本轮演示使用可丢弃工作区和可信测试代码 |
| 任意副作用 exactly-once | 不作为交付承诺 | 依赖外部系统幂等与事务边界，通用运行时无法独立保证 |
| 数据与 Trace | 本地受控保存、明确许可与脱敏后导出 | 完整调试资料不自动具有公开分享权限 |

## 9. 简历与项目叙述的可写边界

本轮完成并通过对应门禁后，可按实际实现使用以下结构，数字从最终报告填入：

> 设计并实现 ForgeHarness 研发 Agent 执行平台，以框架独立运行时统一管理工具权限、预算、审批和调用日志；打通项目知识检索、受控代码修复、验证与补丁交付，通过故障注入验证重启恢复边界，并在版本固定的真实任务集上评估成功率、引用支持和执行成本。

若某项仍未完成，应删除或明确标注计划状态。涉及“提升 X%”“节省 Y%”必须同时说明基线、样本、模型、预算与测试环境。保留实验中的负结果，例如 Reviewer 没有收益或复杂编排成本更高，它们能够证明工程判断。
