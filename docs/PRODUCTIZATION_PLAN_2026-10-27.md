# ForgeHarness 现有能力产品化与落地交付计划书

日期：2026-10-27。状态：执行中，不是发布报告或业务合格证明。P0 范围与契约已建立在
`reports/productization-20261027/`；当前已完成受限参考应用的 P1–P4 工程实现，正在运行质量门禁，真实宿主接入与业务验收仍受外部依赖阻塞，不得据此声称最终交付。逐项状态见
[产品化执行状态](../reports/productization-20261027/IMPLEMENTATION_STATUS.md)。

## 1. 目标与完成定义

以历史 SDK 0.9.1 / API v1 为起始框架基线，本轮变更分配 SDK 0.9.2 工程候选身份；冻结核心功能扩展范围，选择一个具体业务场景，把已有能力完善为可安装、可操作、可维护、结果可验收的受控内部应用。

首版完成标准：一位未参与核心开发的使用者，能够依据交付文档完成安装、配置和真实任务；任务需要审批或发生异常时，使用者与管理员能按权限和手册处理；服务重启后状态可核对，数据可以按支持范围备份还原，业务结果有独立验收证据。

交付结论分别记录：

| 结论 | 所需证据 |
| --- | --- |
| 框架工程合格 | 绑定源码与发行物的完整质量、契约、安全、依赖及干净副本门禁 |
| 应用接入合格 | 固定宿主版本上的身份、资料、工具、会话、审批、恢复与操作入口验收 |
| 业务试点合格 | 真实目标模型、授权业务资料、预先约定的评分与实际使用者验收 |

三项分别判定。缺少真实资料、接口或必要评审时，可以完成工程交付，但业务资格保持“未验收”。完成一个受限内部试点不代表具备公网多租户服务或生产高可用能力。

## 2. 基线与证据边界

- 框架：SDK 0.9.2 工程候选 / API v1；Python 3.12，由 `uv` 管理环境；核心不依赖 LangGraph。历史 0.9.1 候选不认证本轮源码。
- 支持形态：单机 POSIX、本地 SQLite、可信宿主、内部受控使用。模型默认并发 1；选择并发 2 时单独验证目标后端。
- 当前工程证据：[并行交付报告](../reports/parallel-execution-20261027/REPORT.md)及其 candidate-r3 验证摘要记录 104/104 门禁通过，源码与干净副本各 1331 项测试通过。
- 本次计划编制只读核对了清单中的 472 个冻结文件，均与文件摘要相符；没有重新执行全套测试。该历史候选不认证本计划新增文件或后续实现。
- 已有预算、权限、审批、恢复、trace、SDK、会话、工作流、固定专家和有界模型并行，以及 CI、健康检查和指标。后续复用这些实现。
- [能力矩阵](CURRENT_CAPABILITIES.md)记录 LexVault 绑定 0.8.3、ForgeCommerce 绑定 0.5.0。核心到达 0.9.2 不表示宿主已经升级；逐宿主选择和验收版本。
- 当前目录没有 Git 元数据，可继续使用逐文件摘要的 archive checkout-equivalent 冻结方式。不得编造提交号；建立正式代码仓库时保留来源与历史证据。
- 历史计划仅作背景。本计划不重新安排已经完成的共享执行器、R2 写入审批恢复、固定专家或有界模型并行开发。

“冻结”指收紧功能范围。确认的缺陷仍需修复并补回归；改变核心实现时使用新版本、新候选身份和新验证记录。

## 3. 首版范围

### 3.1 必交范围

1. 一个选定应用和一条业务主链路。
2. 选定执行路径的任务提交、状态、结果、来源、审批、取消、恢复和诊断入口。
3. 宿主真实身份与资源授权接入，以及业务工具的可信回执。
4. 与主链路相关的正常、失败、证据不足、重复请求、重启和撤权处理。
5. 安装部署、健康诊断、备份还原、版本固定、升级回退和数据保留手册。
6. 开发集验证、独立业务终评、真实使用者验收与最终候选审查。

操作界面优先复用现有控制台和 HTTP 适配器。管理员低频操作可以通过经过授权的 CLI 和手册完成，不要求另建完整后台系统。

### 3.2 业务场景选择

建议优先评估电商咨询与人工工单，因为业务成功条件较清晰；这是计划建议，尚未替用户选定商家、接口或实际数据。P0 根据真实资料和负责人是否可用，确定以下一条主线。

| 主线 | 首版闭环 | 所需外部条件 |
| --- | --- | --- |
| 电商咨询与人工工单，建议优先 | 登录 → 授权商品/FAQ 查询 → 有来源的回答 → 证据不足时澄清或转人工 → 工单回执与查询 | 商品与 FAQ 数据权限、当前价格库存接口、可查询及去重的工单接口、业务验收人 |
| 法律资料问答与审核草稿，可替换 | 登录 → 授权案件资料查询 → 引用回答 → 审批保存草稿 → 独立内容审核 | 当前身份和页级权限、稳定资料版本与撤回信号、法律专业评审人 |

一次只把一条主线纳入首版业务验收。另一条保留已有工程回归，不同时承担真实上线目标。

### 3.3 延期与条件触发项

| 项目 | 本阶段处理 | 重新纳入的条件 |
| --- | --- | --- |
| 自主递归 Agent、动态拆解、更多编排方式 | 延期 | 实际失败案例证明现有路径无法满足已选场景 |
| 并行工具、并行写入、提高并发上限 | 延期 | 目标负载测量证明必要，且隔离与一致性方案另行验收 |
| 分布式调度、多机 HA、通用 exactly-once | 延期 | 单机容量或恢复目标已无法满足业务需求 |
| 通用 IAM、多租户 SaaS、计费系统 | 延期 | 明确转为公网多用户服务；届时扩展账户、隔离、限流和运营要求 |
| 支付、退款、改价、自动下单和外部内容发布 | 不纳入首版 | 有单独业务范围、真实授权和副作用验收 |
| 全量迁移旧宿主、旧状态自动升级 | 不作为前置 | 选定应用确实依赖新能力，且迁移策略经过单独验证 |
| 更多框架性能对比和通用优势证明 | 延期 | 发布目标明确包含相关比较主张 |
| 不可信仓库代码执行 | 不纳入上述两条默认业务主线 | 若改为 Coding 产品，先提供并验证宿主系统沙箱 |

## 5. 分阶段任务与验收

### P0：确定交付契约

任务：

- 明确首版用户、主线、任务输入、最终产物、成功判据及人工接管责任。
- 固定宿主源码身份、SDK wheel 与 SHA-256、模型配置、Python/OS、依赖和状态目录。
- 按应用需要选择 ReAct、WorkflowRunner 或 R2/Collaboration。使用现有会话路径即可满足业务时，不把全面接入所有编排能力列为前置。
- 记录数据与接口授权范围、资料负责人、评审人、部署负责人及计划内允许的写操作。
- 确定开发集和终评集的样本规模、任务分层、评分方法、性能及预算目标。可先使用本文第 6 节的提案，开正式集合前完成冻结。
- 记录工作区范围；涉及外部宿主仓库的实现必须在明确授权的该宿主工作区开展。

交付物：`SCOPE.md`、应用版本清单、验收契约草案、数据与人员依赖表，均放在本轮独立交付目录中。

出口：一个应用、一个部署形态、一个可判定的业务成功定义已经确定。尚未获得的资源明确标为依赖，不写成已具备。

### P1：完成用户操作闭环

任务：

- 接通提交、任务标识、状态查询、预算使用、结果与来源展示。
- 将待审批操作的对象、参数、风险和审批身份展示清楚，支持拒绝或到期后的明确反馈。
- 接通所选路径已有的取消、恢复和事件查询能力；若承诺 R2/Collaboration，补齐它与会话/任务标识、HTTP/UI 的实际映射。
- 明确区分运行中、等待审批、取消已申请、需要对账、失败、预算耗尽和成功。以持久状态及业务回执呈现结果。
- 页面刷新、断线重连和重复提交使用稳定请求标识，避免创建第二次执行。

验收：

- 从一个入口完成一条任务，不依赖开发者临场修改数据库或补 Python 调用。
- 提交、重复提交、刷新、审批、拒绝、取消、重启恢复和结果查看均有应用级端到端测试。
- 未确认完成的任务不显示成功；申请取消不显示成已回滚。
- 非 owner 无权读取任务、历史或结果，错误提示不泄露其他用户对象是否存在。

### P2：接通真实业务与身份

共同任务：

- 复用宿主身份、角色和资源权限，替换公开演示角色与恒真授权回调。
- 每次读资料、读历史、审批和恢复重新检查当前权限及来源版本；策略与副作用类别由可信代码声明。
- 为外部写入建立业务请求去重、可查询回执及超时核对流程。来源失效、外部失败和未知结果都有明确行为。

电商分支：

- 接入实际商品、价格库存、审核发布 FAQ 和工单接口；展示数据来源与查询时点。
- 完成“没有商品匹配/用户描述不清楚 → 澄清或通用人工工单”的分支，不要求必须先选中 SKU 才能获得帮助。
- 工单内容遵循最小必要范围；“已接收”“等待人工处理”“工单已创建”按真实状态区分。
- 验证重复消息、网络超时后的查询以及重复恢复均不创建第二个工单。

法律替换分支：

- 复用已有 LexVault 接入成果，验证正式入口、当前身份、页级权限、稳定版本和撤回事件。
- 引用核验同时检查来源范围与结论支持；缺少证据时拒答或请求补充。
- 执行审批与内容审核分别处理，保存草稿不等于内容已经获得专业认可。

验收：真实账户、授权资料和真实目标接口完成正常链路及关键失败链路；业务负责人核对产物。只有模拟接口通过时，仍标注为参考应用。

### P3：把恢复机制变成可操作流程

任务：

- 提供受授权保护的异常列表、回执查询与诊断信息；高风险管理操作记录操作者、原因、证据和结果。
- 将未发出请求、已知完成、结果未知三类状态分开处理；未知副作用不通过盲目重试解除。
- 对 provider 未决容量提供查询和人工处置说明。`confirm_ended` 只确认物理调用结束，不能凭此把未知用量清零。
- 明确取消超时或适配器无法取消时，何时由宿主停止 worker、如何继续核对远端结果。
- 将确认缺陷补成回归测试；非平凡的身份、事务或恢复设计变更记录 ADR。

最低故障矩阵：

| 场景 | 应有结果 |
| --- | --- |
| 写操作等待审批时服务重启 | 恢复同一待审批任务，审批仍绑定原操作与当前身份 |
| 回执丢失或外部超时 | 保留未知状态与预算预留，先查询原回执，不自动重发 |
| 重复提交、重复批准、重复恢复 | 无第二次副作用；过期或重复授权被拒绝 |
| 执行中撤权或来源失效 | 停止后续授权操作，不披露无权结果，已发生用量仍结算 |
| 预算耗尽或 deadline 到达 | 准确终态，不因重启得到新预算或新期限 |
| 取消时已有请求在途 | 展示真实取消进度，最终结果和消耗按证据处理 |
| provider 有未决 claims | 保守停发，有明确管理处置步骤及审计记录 |

出口：每类场景有回归或故障演练记录；使用者能识别异常，管理员能依据手册处置。范围内的泄露、未批准写入、重复副作用和虚假完成均为零。

### P4：部署与数据生命周期

任务：

- 为选定部署形态统一安装、配置检查、启动、停止和状态查询，复用现有健康检查与指标。
- 区分应用服务与外部模型/依赖服务的管理责任，不隐式启动或停止用户的其他服务。
- 记录模型不可达、磁盘不足、队列拥塞、待审批积压和未决调用的诊断步骤；需要通知时使用选定运维渠道。
- 核对探针鉴权。当前 README 对 metrics 的描述与代码白名单存在偏差；应校正文档和部署配置，不为适配探针放宽敏感端点授权。
- 明确保留与删除对象：会话、运行、审批、trace、provider 容量账本、资料、附件、业务回执、导出物和备份；列明责任人与保留期限。
- 固定 wheel、依赖、应用配置和模型身份；升级时先验宿主兼容，旧运行保留创建它的版本与配置，新旧状态分开管理。

备份与恢复验收：

1. 在隔离的演练实例中，按手册停止新任务准入并协调本地写入者，建立相关数据库、文件和外部回执引用的一致性备份；不把复制一个正在写入的 SQLite 主文件当作完整备份。
2. 记录备份摘要、版本、目录身份、恢复点和未决任务。无法确认结束的远端调用继续保持未知。
3. 在该演练实例的**同一机器、相同绝对路径、相同 wheel 和执行配置**下还原并重启，检查任务、审批、trace、容量账本与回执对应关系。
4. 验证已完成副作用没有再次执行、旧任务可按契约继续，记录实际恢复时间及恢复点；由负责人判断是否满足事前设定的 RTO/RPO。
5. 演练不覆盖或破坏真实在用数据。跨路径、跨机器恢复和状态迁移另立方案，不从本阶段演练推出支持结论。

路径限制依据：provider identity 包含绝对容量目录，执行配置参与运行身份。已有 invocation ID 会持久复用，但这不等于整个运行支持任意目录迁移。

出口：新环境可以按文档安装和完成任务；启动、重启、带凭据探针、备份还原、版本回退和保留删除流程都有实测记录。回退不让旧 wheel 接管新格式的在途状态。

### P5：开发质量与独立使用体验

任务：

- 在开发集上修复模型格式不稳定、错误澄清、错误引用、错误转人工和 UI 使用问题。
- 固定模型、提示词、工具、预算和观察格式的版本；改变任一项时记录差异及回归结果。
- 用真实目标环境测量任务级 p50/p95、实际 provider usage、失败消耗和人工介入；没有可靠用量时标记未知，不填零。
- 请未参与核心实现的使用者按文档安装并完成主链路和一项异常处置，记录卡点、人工帮助和完成时间；不能代填为独立验证。
- 整理当前文档入口、版本说明与支持范围，历史材料保留版本身份，修正文档与实现不一致的部分。

出口：开发集达到候选目标，已确认 blocker/high 缺陷关闭；真实使用者暴露的问题完成分类与修复或明确接受。正式终评数据尚未用于调参。

### P6：冻结、审查、终评与发布交付

按以下顺序执行：

1. 冻结本轮源码、宿主、wheel、锁文件、模型配置、工具、提示词、数据、评分、预算与目标环境；在独立目录建立候选身份。
2. 运行源码侧全部适用质量与评估门禁，并审查架构、正确性、测试、安全边界、依赖、文档和公开能力声明。
3. 对每项发现记录等级、范围、状态和证据；修复 blocker/high，确认缺陷增加回归测试。任何候选输入变化都生成新候选并重新验证。
4. 从冻结清单建立干净 checkout-equivalent 副本及新 Python 3.12 环境，重跑全套适用门禁，验证 wheel/sdist、最小安装、示例和宿主行为。
5. 工程候选稳定后，先落盘不可覆盖的终评声明，再按既有封存消费规则执行正式业务终评和人工评分；全部失败、消耗与基础设施异常保留。
6. 若终评导致调参或源码修复，旧结果保留，重新冻结并执行所需门禁；使用新的独立终评集，不能反复消费原集合挑选通过结果。
7. 完成部署及使用者验收，分别出具工程、宿主接入、业务质量结论；记录残余风险、适用版本、维护责任和重新评审条件。

必须保留的工程门禁：全量 format/lint、mypy、测试、纯分支覆盖率至少 85%、keyless 控制及开发评测、范围内业务契约与安全测试、恢复测试、锁文件检查、依赖审计、发行物成员及摘要、最小安装、宿主集成和干净副本复验。已有检查不因转入产品化而删除；历史依赖例外须重新确认适用性。

出口：本次候选所有必需验收项均有通过证据，或交付明确降为工程/参考应用状态；不得把尚未完成的业务或部署验收写成“完整项目已完成”。

## 6. 业务验收指标提案

以下沿用 [quality-targets.json](../evals/business/quality-targets.json) 的提案，尚非业务负责人已批准的指标。P0 确定定义，P6 开集前冻结；不得看见终评结果后降低门槛。

| 指标 | 建议门槛 | 计量要求 |
| --- | --- | --- |
| 引用范围、版本和精确位置正确 | 100% | 单列需引用任务与引用条目分母；不代替语义支持评分 |
| 可核验事实正确率 | ≥95% | 明确事实单元、资料时效和裁决方式，任务级成功率另报 |
| 应澄清或转人工场景处理正确率 | ≥95% | 单列无证据、冲突、超权限和描述不清等任务族 |
| 跨范围泄露、未批准副作用、重复副作用、虚假完成 | 0 | 任何一次即阻断该候选资格，不用总体平均分抵消 |
| 结论获证据支持、法律专业质量 | 领域量表 | 由合适领域评审人评分并记录分歧；法律场景必须有专业评审 |
| 时延、预算和成本 | P0/P5 校准，终评前固定 | 分任务族报 p50/p95、实际 tokens、失败消耗；无定价或用量时不编造金额 |
| 恢复时间和恢复点 | 按目标使用场景事前确定 | 基于 P4 实测，不把进程重启成功等同于满足业务恢复目标 |

样本设计：建议先准备 30–50 个开发任务与 60–100 个独立终评任务，实际规模由资料覆盖、任务分层和评审资源决定。这是工作量起点，不是统计充分性的保证。重复采样单列次数，不能当作新增独立题目；报告样本数、任务族、失败及区间或样本限制。

现有确定性业务契约、作者自建库存算术题和合成封存夹具继续用于各自的工程目的，不直接作为真实业务合格证据。缺少独立数据或必要评审时不得打开正式终评并声称通过。

## 8. 分工、依赖和执行规则

| 责任角色 | 负责事项 |
| --- | --- |
| 项目/业务负责人 | 选定场景、数据授权、成功标准、适用范围与残余风险接受 |
| 工程实施者 | 接入、操作流程、缺陷修复、测试、ADR、构建与候选证据 |
| 运维责任人 | 目标环境、凭据、备份、恢复、异常处置、升级与维护手册 |
| 领域评审人 | 业务答案与产物评分；法律场景提供必要专业判断 |
| 独立使用者 | 按交付文档实际安装使用并记录卡点，不由实施者代填 |

同一人可以承担多个工程角色；独立使用者记录和专业评审不得伪装为已完成。审查若由实施者自审，报告应明确其性质。

执行规则：

- 每个工作包结束即给出变更、验证、遗留项和是否满足阶段出口。
- 新功能请求进入后续清单；只有首版闭环阻塞或已确认缺陷进入当前实施范围。
- 每项行为变化及缺陷修复补测试；重要架构决策记入 `docs/adr/`。
- 模型输出和工具参数继续在边界验证，状态/预算/审批/权限由确定性代码持有。
- 只修改任务明确授权的工作区；应用领域逻辑留在宿主，不将法律或电商分支写进通用核心。
- 发布或真实外部操作遵循实际授权范围；计划内的模拟回归不充当真实业务执行证据。

建议执行顺序：**P0 → P1/P2/P4 准备 → P3 → P4 演练 → P5 → P6**。首个动作是确定一条业务主线及其可用数据和接口，然后按阶段出口推进。
