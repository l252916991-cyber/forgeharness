编制日期：2026-10-06  
状态：完整业务平台仍为计划；商品/模拟工单参考应用及 0.3.0 的咨询/内容草稿公共模块已有实现，

框架依赖：[ForgeHarness 框架演进计划书](FRAMEWORK_EVOLUTION_PLAN.md)。本文负责业务应用，底层执行能力由该框架提供。

## 1. 产品目标与交付边界

围绕一家模拟商家的商品咨询，建设“商品与知识整理 → 有依据的咨询 → 人工接待 → 运营内容 → 员工训练 → 质量反馈”的电商 Agent 平台。让咨询、运营、培训使用同一套商品事实、知识版本和执行记录，验证 ForgeHarness 能承载第二种业务。

首版用户是消费者、客服和商家管理员；后续加入运营人员、培训负责人。消费者获得带依据的商品说明，客服接收结构化转接工单，管理员管理资料与审核。首版使用一个演示商家、另一个隔离验证租户、模拟商品与订单 API，在本机或受控环境运行。身份与数据权限从第一版开始设计，但这不等于已具备生产多租户平台能力。

MVP 交付四项：商品咨询、最小数据整理、版本化知识管理、人工转接工单。电商交易系统提供商品、价格、库存、订单等事实；本项目不自行实现支付、仓储和物流平台。退款、改价、自动营销和真实渠道外发属于后续扩展，不能成为首版完成条件。

业务价值通过记录“回答正确性、客服接手所需信息、人工处理时间、内容审核通过率”评估。销量、转化率、营收和人力节省只有在获得真实业务数据与适当比较条件后才能报告，本计划不预设提升百分比。

## 3. 模块规划与业务闭环

| 模块 | MVP 内容 | 后续内容与启动条件 |
| --- | --- | --- |
| 商品咨询台 | 需求澄清、参数说明、商品对比、引用、缺证据转接 | 有真实渠道授权后接入店铺或私域消息 |
| 数据工作台 | CSV/JSON 导入、必填字段与单位校验、重复记录处理、失败清单 | 数据量和更新频率证明需要后，增加任务队列和增量同步 |
| 知识管理 | 文本/图片来源、草稿审核、发布版本、停用旧内容 | 增加视频字幕与时间位置索引；不直接将未审核 OCR 当事实 |
| 客服工作台 | 工单、对话摘要、已核验事实、待确认问题、状态流转 | 接真实客服系统后增加双向状态同步 |
| 运营工作台 | 暂不纳入 MVP | 商品卖点、文案和脚本草稿、审核记录、模拟发布 |
| 员工教练与质检 | 暂不纳入 MVP | 场景练习、证据评分、人工复核；不自动形成雇佣决策 |
| 效果工作台 | 失败标签、反馈记录、运行与数据版本 | 候选提示词/检索策略比较，按门禁发布和回滚 |

四个闭环分别落到可观察记录：业务闭环是咨询到工单处理结果；技术闭环是失败到修正再到回归；成长闭环是脱敏案例到员工练习与人工反馈；生态闭环是工具适配器和应用契约可复用。每条闭环应有负责人、状态和验收证据，页面数量不作为完成标准。

## 4. 架构与共享数据链路

```text
消费者咨询页 / 客服台 / 商家管理台
                  │ 认证、会话与应用权限
                  ▼
          电商应用服务（业务规则）
    咨询 │ 工单 │ 数据知识 │ 草稿 │ 教练
                  │ C1–C8 目标契约
                  ▼
             ForgeHarness
     循环 / 工具校验 / 预算 / 审批 / 恢复 / Trace
                  │ 经策略允许的工具调用
       ┌──────────┼───────────┐
       ▼          ▼           ▼
  商品/订单 API  知识检索服务  工单/素材模拟服务
```

框架与应用先保留在同一仓库以便协作，通过包与依赖边界分开。应用暂定名为 ForgeCommerce，建议目标落点为 `apps/forgecommerce/`，不是当前已存在目录的声明。应用依赖框架公共接口；核心不得导入电商应用，不得出现按 `commerce` 分支判断的运行逻辑。Python 3.12、uv 沿用仓库要求。

共享数据链路：许可明确的资料进入暂存区，完成字段与来源校验后，由管理员审核发布；检索索引绑定该发布版本。咨询将静态知识与实时 API 事实组成上下文，输出回答和证据。工单、素材与训练题保留同一商品与资料版本引用；反馈形成待审改进候选，经过评测再替换版本。

| 应用数据实体 | 关键字段与约束 |
| --- | --- |
| `Tenant / Principal / Role` | 可信租户、用户、角色与资源范围；由认证与应用数据库确定 |
| `Product / SKU` | 商家内唯一 ID、规格、单位、来源版本；可售价格与库存读取结构化 API |
| `KnowledgeAsset / Revision / Chunk` | 来源、许可、摘要、审核状态、有效期、图文或视频位置；停用版本退出在线检索 |
| `Conversation / Turn` | 所属用户、权限范围、运行引用、问题与经处理的模型可见内容 |
| `Ticket` | 关联咨询、人工摘要、责任人、状态、幂等键；不保存无关身份信息 |
| `ContentDraft / Review` | 事实引用、内容版本、审核人、审核结果、模拟发布状态 |
| `TrainingCase / Feedback / EvalCase` | 来源许可、标注、数据分区、版本、评审记录；评测集限制访问 |

所有表、检索过滤、缓存键和对象存储引用均携带服务端确定的租户范围。向量相似度不是授权机制。模型不能通过传入另一个 `tenant_id` 扩大范围；会话串联、批量导出、素材检索也必须执行相同隔离规则。

## 5. 与框架的复用契约

下表沿用框架计划的 C1–C8 编号，表示目标接口。现有实现能否直接满足契约，需要 F0 核对与后续迁移确认。

| 契约 | 框架提供 | 电商应用提供 |
| --- | --- | --- |
| C1 `ApplicationSpec / RunContext` | 应用装配、可信上下文与 Scope 传递 | 认证主体、租户、订单归属、资源范围、任务类型 |
| C2 `Model` | 模型协议、预算计量与适配边界 | 各任务模型配置、输入与输出约束；不依赖特定厂商 |
| C3 `Tool` | 参数校验、调度、超时、输出限制 | 商品、库存、工单、素材工具及副作用声明 |
| C4 `ToolPolicy + ApprovalLedger` | 调用前强制策略检查与审批事实保存 | 业务权限、何时需要人工确认、可审批人的权限 |
| C5 `CheckpointStore + InvocationJournal` | 状态恢复、调用结果复用、不确定结果处理 | 业务幂等键、查询调用结果的方法、业务状态映射 |
| C6 `ContextProvider / Knowledge` | 上下文预算、检索接入与来源记录 | 商品知识、用户授权范围、文档有效性与实时数据优先级 |
| C7 `Verifier` | 执行验收并给出结构化结果 | 咨询、工单和内容草稿的完成条件 |
| C8 `Trace / Evaluation` | 运行记录、脱敏接口、评测机制 | 业务指标、标注样例、评分规则与报告 |

复用验收：电商应用使用公共接口完成装配；新业务验收器可替换 Coding 专属验收；运行时间线、预算和审批查询共用框架能力；接入时不复制循环、journal 或审批实现。确实发现通用缺口时，先提交契约与 ADR，再修改核心并让两个应用通过回归。

## 6. 工具、授权与副作用

| 目标工具 | 副作用 | 授权、审批与恢复要求 |
| --- | --- | --- |
| `search_products / get_product` | 只读 | 限定商家与可见商品；返回版本及来源 |
| `get_price_stock` | 只读 | 返回 SKU、币种、更新时间；过期或失败时不编造数值 |
| `search_knowledge` | 只读 | 检索前后校验权限、审核状态和有效版本 |
| `get_order_status` | 敏感只读，后续接入 | 后端核验用户与订单归属；模型知道订单号不构成授权 |
| `create_handoff_ticket` | 创建业务记录 | 用户明确请求转接并确认摘要；服务端策略校验，以幂等键去重 |
| `save_content_draft` | 写入草稿 | 仅运营角色；限定工作区与商品范围，同一调用可查询结果 |
| `publish_knowledge_revision` | 改变在线知识 | 管理员审批具体版本与摘要；切换版本留记录且可回滚 |
| `simulate_publish` | 写入模拟发布记录 | 审核内容版本、目标模拟渠道；不得产生真实网络外发 |

审批绑定租户、执行主体、工具、规范化参数摘要、资源、内容版本、有效期及一次性使用状态。修改文案、渠道或商品后，旧审批不再适用。工单等低风险动作是否要求独立审核，由应用策略明确配置；用户确认与管理员审批必须区分，不能用模型自述充当任一种授权。

任何写入都需区分“未执行”“已完成”“结果未知”。模拟服务也要实现幂等键与结果查询：工具超时后优先查询该逻辑调用是否已生效，核对成功后复用结果；无法确认则进入待核对状态，不自动重放。未来接真实渠道时逐项核对对方 API 能力，不承诺任意外部系统的 exactly-once。

业务去重另有一层：重复点击或重新提交可能生成新的 run_id，不能只依赖框架的 logical_call_id。应用为同一业务请求保存稳定 request_id/操作键，并在工单、模拟发布等业务账本建立唯一约束；键由服务端生成和验证，模型不能通过更换键绕过约束。声明为幂等的工具必须有这些实现依据。

隐私边界：不收集无关地址、电话或支付信息；练习与评测优先使用合成、许可明确且脱敏的数据。知识材料、用户消息和工具返回均视为不可信输入，其中“忽略规则”等文本不能改变权限。凭证只留在服务端秘密存储，禁止进入模型输入、仓库和 Trace。

可重建性要求针对实际模型输入与工具结果实现：模型调用前完成必要脱敏；受控证据存储记录最终输入、来源版本和调用摘要，公开报告仅含脱敏引用。保留期限与删除策略由应用定义，删除后明确标记相应证据不可重建，不能同时声称无限可回放。

同一身份权限、保留期限与删除规则覆盖 checkpoint、journal、Trace、附件、训练候选和评测导出。不能只删除知识索引而遗漏工具结果或会话快照；恢复必需证据被删除时，该任务不得继续恢复或宣称可完整回放。

## 7. 三条核心工作流

**咨询与转接。** 消费者说明需求 → 澄清必要参数 → 检索审核知识 → 查询当前价格/库存 → 生成带来源回答 → 验收事实与引用。资料冲突、超出知识范围或用户要求人工时，生成工单摘要并确认，创建工单后展示编号。验收要求回答中的商品、数值与证据匹配，或正确转接；“模型认为已完成”不构成成功。

**运营草稿。** 运营人员选择商品与目标人群 → 获取可使用的卖点和限制 → 生成文案/脚本草稿 → 检查事实、禁用声明与素材许可 → 人工审核 → 模拟发布。没有证据的性能、认证和效果承诺必须删除或待人工补充。图片或视频生成属于可插拔能力，首个交付可以只有文字草稿。

**员工练习与反馈。** 脱敏对话转为训练候选 → 人工确认题目与参考依据 → 员工练习 → 按信息准确性、澄清、服务规范评分 → 展示证据并允许人工复核 → 将普遍错误反馈到知识或课程修订。模型分数不直接等同于实际销售能力。

默认采用单 Agent 加确定性服务流程。独立引用检查、素材评审等只有在同模型、相同任务与预算口径下，提高质量且成本可接受时才引入第二个 Agent；权限、审批和状态始终由运行时执行。所谓自进化先实现“提出候选 → 人工审核 → 离线评测 → 小范围试用 → 发布/回滚”，禁止静默改写生产工具或策略。

## 8. 数据、评测与目标

起步数据建议：30–50 个模拟商品及 SKU、20–30 份许可明确的商品说明/常见问题、若干商品图片、模拟库存与工单。所有合成资料明确标注，不能称为真实商家生产数据。价格、库存、促销资格等易变字段不依赖文档向量作为最终依据。

准备 80 个开发案例、60 个全新封存 holdout 案例，覆盖咨询、比较、跨轮追问、资料冲突、无证据、时效数据、转接；另建至少 40 个确定性权限、提示注入、审批与恢复案例。按商品族、模板或对话来源分组切分，避免近重复泄漏。用于改提示词或挑模型的案例归入开发集；最终 holdout 由独立保管/评审流程控制，揭示后即作为历史终评集，不再冒充未见数据。

标注需包括允许引用、事实答案、预期工具、授权范围、成功/转接条件和错误类型。至少对一部分案例进行双人或隔离复核，记录分歧；自动评分和模型裁判需抽样人工检查，不能仅用另一个模型认可作为正确性证据。

| 指标 | 初步验收目标，均未实测 |
| --- | --- |
| 咨询任务成功率 | 全新 holdout ≥85%；每个关键类别单列，不用总分遮盖缺陷 |
| 有证据事实正确率 | ≥90%；明确分母为可核验事实项 |
| 引用支持率 | ≥95%；来源存在与支持具体结论分别评分 |
| 无依据时正确澄清/转接 | ≥90%；记录错误拒答对体验的影响 |
| 实时价格/库存 | 所有展示数值可追溯到本次 API 结果；测试集内不得自行编造 |
| 隔离、审批与重复副作用 | 固定边界与故障案例中零越权、零审批绕过、零重复写入；不外推为系统绝对安全 |
| 时延与成本 | 报告模型、硬件、并发条件下的 p50/p95、token、工具次数；本地推理不将 token 折算金额，付费 API 仅在有实际账单或明确计费记录时列金额；终评前冻结预算 |
| 人工与业务效果 | 记录转接完整度、人工处理时间、草稿修改量；没有真实试用时不宣称提升 |

先建立系统基线，再在相同模型、任务、权限和实时事实接口下逐项比较知识检索、混合检索/重排和上下文策略。需要比较“仅问答”和“问答加工具”整套方案时，明确这是系统组合差异，不能把全部收益归因于某一个模块。之后再决定是否试验多 Agent 或微调。报告绑定源码、框架、模型、数据与评分器版本。

真实模型终评建议每题至少 3 次，既报告逐题成功次数，也报告整体分布；重复采样不能被当作新的独立题目。开发集基线完成后、首次打开 holdout 前冻结目标、预算、评分规则和中止条件。未达目标时保留候选状态，不能因分数不佳删除案例或降低门槛；若据终评调整实现，旧集合转为回归集，新的终评需重新封存。

微调仅在错误分析表明稳定风格/格式或领域行为难以通过数据、检索、工具与提示解决，且有足量合规训练数据时立项；动态价格和权限规则不通过微调灌入模型。

## 9. 阶段、依赖与验收

净工程量预估 100–146 小时，可按 100–150 小时规划；这是电商应用增量，不包含框架建设，也不包含模型调用、素材生产、外部渠道申请和人工标注等待。每阶段增加相应行为测试与回归；本次仅编写计划，不运行代码或评测。

| 阶段 | 工程量 | 框架依赖 | 交付与退出条件 |
| --- | --- | --- | --- |
| E0 数据与模拟业务 | 10–14h | F0；接口设计可并行 | 商品/知识模式、模拟 API、身份范围、数据分区与指标口径草案；确认来源许可和未实现项，终评规则在 E4 定稿冻结 |
| E1 咨询 MVP 与人工转接 | 22–30h | 只读装配依赖 F1/F2；工单写入及恢复依赖 F3 | 多轮咨询、实时事实、引用、知识审核、转接工单可完整运行；形成 F4 的第二应用接入证据 |
| E2 运营草稿与审核 | 16–24h | F3/F4，业务依赖 E1 | 文案与脚本草稿、版本审批、模拟发布；过期审批失效、重试不重复写入 |
| E3 教练/质检与视频素材 | 20–30h | F4/F5；业务数据来自 E1/E2 | 先交付文字练习与证据评分；再做字幕/片段索引，视频自动剪辑可独立延期且明确标记 |
| E4 评测反馈与候选改进 | 20–30h | F5，前阶段持续积累案例 | 开发集回归、错误分类、候选策略比较与回滚演练；微调仅输出可行性判断，不默认训练 |
| E5 联合审计与演示 | 12–18h | E4、通过 F6 的明确框架版本 | 冻结应用与框架版本组合后运行封存终评及全部适用门禁；修复 blocker/high、补回归，干净检出等效复验，列残余风险与实施边界 |

E1 是首个可交付业务版本；E2–E4 可以分批发布为演示能力。F4 使用 E1 的接入结果验收框架抽象，不要求等电商全部模块完成。框架通过 F6 后可以先行交付核心与最小参考应用；电商 E5 再针对明确的框架版本做联合验收。若电商开发要求修改核心行为，相应核心必须重新通过受影响门禁与发布审计，不能把修改挂在旧 F6 报告下。任一侧仍有发布阻断项，联合版本不得标记完成。

## 10. 演示与对外说明

准备三段可复现演示：商品追问与实时库存变化；无证据转接并在创建工单后模拟中断恢复；从同一商品知识生成草稿、修改内容导致旧审批失效，再完成模拟发布。每段显示实际运行 ID、数据版本、工具证据、成本与失败处理，不用预录成功结果冒充在线执行。

完成后可据证据描述为：“基于自研 ForgeHarness 实现电商咨询与运营参考应用，复用受控工具、审批、状态恢复和评测契约，使用版本化商品知识和结构化业务 API。”具体通过率、案例数和耗时只填最终报告的真实值。

对外必须区分模拟业务、受控试用和真实上线。尚未接渠道时不写“已接入电商平台”；没有真实经营数据时不写“提升转化”；没有训练与独立评测时不写“完成微调”；未通过联合审计时不写“生产级框架与平台已完成”。
