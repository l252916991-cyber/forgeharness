## 1. 定义的六个谓词

定义句可以拆成六个必须同时成立的谓词。任一不成立，产品就退回上一形态（托管的单租户应用 / 单机参考应用）。

| 谓词 | 判定问题 | 常见反例（不算） |
| --- | --- | --- |
| **P1 同一套代码** | 所有租户是否运行同一个构建产物，差异只来自配置与数据？ | 给大客户单独部署一套并称为 SaaS；`if tenant == X` 分支；per-tenant 代码补丁 |
| **P2 同时服务多个** | 是否共享容量池，且单租户突发不破坏他人 SLO？ | 每客户一套部署（成本线性）；单租户独占 worker；靠人工扩容 |
| **P3 互不知情** | 是否既读不到、也无法推断他人存在？ | 越权返回 404 但 403 泄露存在性；共享向量索引泄漏他人片段；错误文本含他人 ID |
| **P4 能收钱** | 用量到到账是否闭环、可对账、可退款、可催收？ | 只有配额限制没有账本；账单靠人工表格；超额静默吸收 |
| **P5 能承诺 SLA** | 是否有可测量的 SLO、信用条款、排除项、事故沟通？ | 写“99.9%”但无测量口径；无排除项；无状态页；SLO 达标客户无感知 |
| **P6 能恢复** | 分级 RTO/RPO 是否实测，恢复后是否一致？ | 只备份不演练；对外报设计值；恢复后重复创建工单 |

### 1.1 词义边界

| 词 | 本计划含义 | 不表示 |
| --- | --- | --- |
| 通用 | 应用中立核心 + 打包应用契约，由第二个非电商应用实证 | 开放平台/PaaS 生态、插件市场、对外扩展 API |
| 生产级 | SLO 达成、变更可回滚、DR 实测、事故有流程、合规有证据 | “测试通过”“能部署”“单机跑得稳” |
| SaaS | 多组织自助开通、按用量计费、隔离与配额、SLA 与信用 | “部署在云上”“支持多人登录”“有 Web 界面” |

### 1.2 四种形态对照

| 能力 | 当前：单机参考应用 | 生产级单租户 | 多租户 SaaS（本目标） | 开放平台（不在范围） |
| --- | --- | --- | --- | --- |
| 真实身份 | 演示角色字符串 | 真实 IAM + 撤权即时 | 多组织 + SSO/SCIM + 席位 | 第三方应用授权 |
| 数据/模型 | 合成 + fixture | 授权数据 + 真实模型 | 多租户 + 模型路由与配额 | 第三方接入 |
| 写入闭环 | 工单只读 | 写 + 幂等 + 未知结果核对 | 同上 + 跨租户隔离 | 第三方写回 |
| 计费 | 无 | 无（合同/内部结算） | 计量 → 账本 → 发票 → 对账 | 分成结算 |
| 可靠性 | 同机同路径恢复 | 实测 RTO/RPO + 告警 | SLO + 错误预算 + 状态页 + 信用 | 多区域 |
| 通用性证明 | 不适用 | 不适用 | 第二应用不改核心 | 第三方不改核心 |
| 团队门槛 | 1 人 | 1–2 人 | 3 人以上含值班 | 组织级 |

**两段式结论**：当前 → 生产级单租户约 100 有效人日；生产级单租户 → 多租户 SaaS 约 +120~200 人日。两段不能合并宣称。

## 3. 为什么“单机内部受控”不满足这套定义

用六个谓词逐一对照，就能说明上一版结论为什么必须保留边界：

| 谓词 | 当前单机部署的实际状态 | 结论 |
| --- | --- | --- |
| P1 | 无构建产物，应用与宿主共用工作树；配置分散在环境变量与路径 | 不满足 |
| P2 | `model_concurrency=1`，容量按进程计，无队列公平性 | 不满足 |
| P3 | 有对象级授权与审计，但“租户”是逻辑字段而非隔离边界；无 RLS、无每租户密钥 | 部分 |
| P4 | 无计量、无账本、无发票 | 不满足 |
| P5 | 无 SLI/SLO、无 on-call、无条款 | 不满足 |
| P6 | 有同机同路径恢复与 manifest 校验；无实测 RTO/RPO、无跨区、无租户级恢复 | 部分 |

因此当前可用的表述是：**框架工程合格 + 单机参考应用闭环可用**；不可用的是：公网多租户、分布式高可用、跨机跨版本迁移、开箱即用的电商生产系统。这条边界与上一轮结论一致，本文件只是把它变成可计数的证据表。

## 5. P1：同一套代码

### 5.1 要求

- 单一构建产物（镜像 digest + SBOM + 签名）服务所有租户与环境晋级。
- 租户差异只允许出现在：DB 行、配置中心键值、feature flag、套餐额度。
- 禁止：per-tenant 分支、per-tenant 补丁、per-tenant 构建、按客户改 schema。
- Enterprise 专属实例允许“同 artifact + 独立数据库 + 独立 KMS”，仍属同一套代码；不允许另起分支。

### 5.2 CI 门禁

| 门禁 | 实现 |
| --- | --- |
| 租户特判扫描 | 对 `org_id`/`tenant` 字面量比较做静态检查，命中即失败 |
| 单产物校验 | 部署清单中的 image digest 必须全环境一致（按晋级路径） |
| 配置完整性 | 新配置项必须有 schema、默认值、文档，缺一失败 |

## 6. P2：同时服务多个

### 6.1 公平性要求

共享容量池必须能回答：一个租户把配额打满时，其他租户的 p95 会劣化多少。目标 ≤10%，超过即视为容量设计缺陷，而不是“正常波动”。

| 机制 | 作用 |
| --- | --- |
| 四层配额 | 运行 → 用户 → 租户 → 平台；软限告警、硬限拒绝、紧急熔断 |
| 公平调度 | 队列按租户加权轮转，单租户并发上限为全局 20% |
| 隔离的 worker 池 | 免费层与大客户可由不同池承载，但同源代码 |
| 退避与降级 | 供应商 429/5xx 时降级模型档位，不把错误传给终端用户 |

### 6.2 容量模型

```
峰值 QPS     = 日请求 × 峰值集中系数(0.15–0.25) / 3600
并发模型调用 = 峰值 QPS × 平均模型调用次数(2–4) × 平均单次耗时(s)
worker 需求  = 并发模型调用 / 单 worker 并发（受 provider 限流约束）
公平性余量   = 单租户上限 20% × 全局并发
```

设计点：300 租户 / 3,000 MAU / 30,000 咨询日 / 120 并发会话 / 60 并发模型调用，压测按 2×。

## 7. P3：互不知情

“互不知情”比“读不到”更严：**不能读到，也不能推断存在，不能通过内部人绕过，不能在备份与日志里残留。**

### 7.1 三防线

1. 应用层：仓储强制接收租户上下文，**不提供默认租户**；无上下文即抛错。
2. 数据库：PG RLS `USING (org_id = current_setting('app.org_id')::uuid)`；应用不以超级用户运行。
3. 密钥层：每租户数据密钥信封加密；删除租户即销毁密钥（crypto-shredding）。

### 7.2 侧信道清单（专项测试）

| 通道 | 风险 | 要求 |
| --- | --- | --- |
| 错误码/文本 | 403 泄露存在性 | 越权与不存在返回同构响应 |
| 响应时序 | 存在性可被差分推断 | 关键路径时间差 ≤ 可忽略阈值 |
| ID 枚举 | 顺序 ID 泄露规模 | 使用不可猜标识 |
| 搜索/联想 | 返回他人条目 | 检索前强制租户过滤，索引层再校验 |
| 向量索引 | 近邻泄漏片段 | collection 按租户隔离或过滤前置 |
| 对象存储 | 前缀列举 | 每租户前缀 + 禁止 list |
| 日志检索 | 运维界面跨租户 | 查询强制注入租户过滤 |
| 导出/备份 | 下载链接越权 | 一次性签名 + 审计 |
| 计费账单 | 暴露他人用量 | 账单只含本租户行项 |
| 状态页 | 事故披露含他租户名 | 对外文案去标识 |
| 模型供应商 | 日志/训练/区域 | 零保留 + no-training + 区域绑定，有合同与配置证据 |
| 内部人 | 运营后台随意查看 | break-glass + 双人审批 + 客户可见的访问审计 |

### 7.3 删除正确性

删除必须同时满足：行删除（≤30 天）、密钥销毁、备份到期清理、恢复流程拒绝复活（墓碑校验）。**恢复旧备份不能让已删租户数据复活**，这是 P3 与 P6 的交叉证据（第 12、24 条）。

## 8. P4：能收钱

### 8.1 管道

```
运行时 → usage_event(幂等 event_id) → 账本(append-only)
      → 小时聚合 → 套餐计数器 → 账单行 → PSP 订阅/发票
      → 日对账（账本 vs 供应商 vs 发票）→ 漂移告警 → 出账闸门
```

### 8.2 计量项与硬要求

计量项：`model_tokens_in/out`、`tool_calls`、`run_seconds`、`knowledge_docs`、`storage_gb_month`、`seats`、`webhook_deliveries`、`egress_gb`。

| 要求 | 判据 |
| --- | --- |
| 幂等 | 同 `event_id` 只计一次 |
| 可重放 | 账本可从原始事件重建聚合 |
| 不丢 | 未知用量标 `unknown`，不记 0 |
| 不重复扣费 | PSP webhook 幂等键 + 去重表 |
| 可对账 | 日对账漂移 <0.5%，超标阻断出账 |
| 可退款 | credit note 与发票一一对应 |
| 可审计 | 每次计价记录单价版本与输入 |
| 可催收 | dunning 三次 → 只读降级 → 停用（数据保留 30 天） |

### 8.3 套餐与单位经济

| 能力 | Free | Team | Business | Enterprise |
| --- | --- | --- | --- | --- |
| 席位 / 工作空间 | 3 / 1 | 按席位 / 3 | 按席位 / 10 | 合同 |
| 月运行次数 | 500 | 50k | 250k | 合同 |
| SSO | 无 | 无 | SAML/OIDC | + SCIM |
| 审计导出 | 无 | 30 天 | 180 天 | 合同 |
| 数据保留 | 7 天 | 30 天 | 90 天 | 可配置 |
| SLA | 无 | 99.5% | 99.9% | 99.95% |

```
月成本 = 固定基础设施 + 模型调用 + 存储 + 出口 + 第三方 + 人力
模型调用 = Σ(tokens_in×p_in + tokens_out×p_out) × (1+重试率) × (1+失败重放率)
毛利 = (订阅收入 − 变动成本) / 订阅收入；GA 目标 ≥ 60%
```

Free 层是获客成本，必须有硬上限与反滥用（卡测试、批量注册、异常用量），不得成为免费模型代理。定价不预设金额，Beta 前用真实成本数据定价。

## 9. P5：能承诺 SLA

SLO 是内部目标，SLA 是合同承诺加信用条款。两者缺一，都只是口号。

### 9.1 SLO 提案值

| 面 | SLI | 目标 |
| --- | --- | --- |
| 可用性 | 非 5xx 成功请求比例 | 99.9%/月 |
| 咨询首答 | p95（不含审批与排队） | ≤8s；工具密集 ≤20s |
| 任务成功率 | 非系统错误完成比例 | ≥99% |
| 审批生效 | 60s 内可见 | ≥99.9% |
| Webhook | 24h 成功投递 | ≥99.5%（8 次退避） |
| 计费账本 | 日对账漂移 | 0 |
| 删除 | 硬删除（含备份） | ≤30 天 |

### 9.2 SLA 条款结构

| 条款 | 内容 |
| --- | --- |
| 测量口径 | 月度可用性 =（总分钟 − 不可用分钟）/ 总分钟；不可用 = 5xx > 5% 持续 5 分钟，或关键功能不可用 |
| 排除项 | 提前 72h 通知的维护窗口、客户侧故障、不可抗力；**供应商故障原则上计入**，仅当降级成功且核心功能可用时剔除 |
| 信用 | 示例：<99.9% 10%、<99.5% 25%、<99% 50%，上限为当月费用的 50%（需法务确认） |
| 申请流程 | 客户提交 → 30 天内核定 → 以 credit 抵扣，不走现金退款 |
| 支持分级 | P1 1h（Enterprise 24×7）、P2 4h 工作时间、P3 1 工作日 |
| 事故沟通 | 首次对外 ≤30min，之后每 60min 更新，结束后 5 工作日复盘 |

### 9.3 错误预算政策

| 预算消耗 | 动作 |
| --- | --- |
| <50% | 正常发布 |
| 50–100% | 发布需额外评审，仅修复类优先 |
| 100% | 冻结非紧急发布，直到预算恢复 |

政策必须有**一次实际执行记录**（第 18 条证据），否则等于没有政策。

### 9.4 人力现实

单人无法承诺 24×7。Beta 阶段只承诺工作时间支持与明确维护窗口；GA 前必须有第二值班人或把 SLA 降到可兑现水平。**把 SLA 写成 99.9% 却无人值班，是比不写更严重的欺骗。**

## 10. P6：能恢复

### 10.1 分级目标

| 场景 | RTO | RPO | 手段 |
| --- | --- | --- | --- |
| 单 AZ 故障 | ≤5min | 0（同步副本） | 托管 PG 自动切换 + 多 AZ |
| 区域故障 | ≤1h | ≤5min | PITR + 跨区副本 + 提升流程 |
| 单租户误删/误操作 | ≤4h | ≤5min | PITR + 租户过滤回灌 |
| 误发布 | ≤30min | — | 镜像回滚 + flag 关闭 + 向前修复 |

### 10.2 租户级恢复的难点

共享库中“只恢复一个租户”需要导出-过滤-回灌，并处理外键与跨租户引用。因此需要：

1. 每日 per-tenant 逻辑快照（可独立回灌）。
2. 恢复前的墓碑表校验（已删租户不得复活）。
3. 恢复后的业务键核对（不重复创建工单/不重复计费）。
4. 恢复本身有审计与客户可见记录。

### 10.3 演练日历

| 频率 | 内容 |
| --- | --- |
| 月度 | 单点恢复（单表/单租户） |
| 季度 | 区域故障切换 + 全量恢复 |
| 每次重大变更前 | 回滚演练 |

对外只报实测值，不报设计值。

## 11. 目标架构

```
浏览器/企业系统/API 客户端
   → 边缘：WAF + CDN + 按 IP/租户/Key 限流
   → 控制面 API（无状态多副本）：身份与租户上下文 / 业务接口 / 幂等入口 / 计量发射
   → Postgres（唯一事实源）+ Redis（缓存队列）+ 对象存储（trace/附件/导出）
   → 数据面 Worker：Harness 循环 / 模型网关 / 外部适配器 + outbox / trace 落对象存储
   → OTel 观测；账本 → 聚合 → 发票 → 对账
```

状态所有权（禁双写）：租户与成员归 API；会话/轮次/审批/运行状态归执行器写、其余读；工单归业务服务；用量归账本；trace 归对象存储。跨组件只走事件或查询。

一次咨询生命周期：客户端生成 `request_id` → API 校验租户/权限/配额、命中幂等即返回 → 同事务写 run + 幂等行并入队 → worker 取租约写 `running` → 需审批转 `awaiting_approval` 释放租约、独立通道决策 → 完成写终态 + 用量事件，outbox 投外部副作用 → 客户端轮询，刷新断线不产生新 `request_id` → 未知结果保持 `unknown`，按业务键核对。

运行状态机：`queued → running → (awaiting_approval ↔ running) → completed | failed | cancelled | unknown`；事件表追加写，当前状态是投影；`version` 乐观锁冲突返回 409；`unknown` 是一等状态。

迁移用 strangler：抽 Store 协议 → PG 适配器 → 影子读比对（不一致即阻断）→ 单租户灰度 → 全量切换并冻结，保留 PITR 回滚。

## 12. 身份、授权与审批

认证分层：自助用 IdP（OIDC）+ 魔法链接；企业 SAML/OIDC + SCIM；机器用作用域化 API Key / OAuth client；高危操作（审批、导出、删除、密钥）要求 5 分钟内 step-up。

迁移自建密码：保留 `identity.py` 的对象级授权与审计，替换密码/令牌实现；`member.idp_subject` 绑定；双运行期标记 deprecated；完成后删除 `scrypt` 路径，回归改 IdP 模拟器。Cookie：`HttpOnly` + `Secure` + `SameSite=Lax` + 8h 绝对过期、无滑动续期。

授权 = 角色权限 ∩ 资源作用域 ∩ 当前状态。`admin` 不得自动获得 `approval:decide` 与 `consult`。审批：独立端点/独立认证/独立审计，四眼原则，批量审批逐项展示，内容变更即旧授权失效。

## 13. 模型网关

六职责：路由（套餐/租户/任务类型，含降级链）、三层限流（超限排队或降级而非 500）、四层预算、成本记账（含重试与未知）、安全（注入检测、内容安全、可配置 PII 脱敏）、审计（输入摘要 + 模型与提示词版本）。

供应商数据边界：零保留选项、no-training 条款、区域绑定、出口审计。这三项同时是 P3 第 11 条证据。

版本治理：`prompt_version`、`model_config_version`、`tool_policy_version` 独立版本化并写入每次运行；变更 5% canary；回滚是配置操作。

评估门禁：每应用开发集 40–60、终评集 60–100 且只用一次；指标含事实正确率（≥95%）、引用有效率（100%）、澄清/转人工（≥95%）、完成率、p95、单任务成本；安全类单列；结果必须带分母、失败样本、版本。

## 14. 首个打包应用

咨询：事实来自工具（价格/库存/FAQ 版本/时间戳），回答带可打开来源；无证据则澄清或建议转人工；多轮时旧事实不作为当前事实。

工单字段：`ticket_id`/`org_id`/`workspace_id`、`requester_id`、`request_id`+`business_key`、`session_id`/`turn_id`、四段摘要（用户原话/工具事实/系统推断/待确认）、`status`/`assignee_id`/`version`、`resolution`/`resolved_by`/`resolved_at`、`sla_due_at`。状态机沿用 `open→assigned→resolved`、`open→cancelled`。

知识与发布：草稿→审核→发布→撤回全程 API + 审计；可查影响面；撤回后新咨询不再使用。

外部适配器四个（商品/库存/FAQ/工单），统一契约 `create`/`get_by_business_key`/`get_status`/`cancel`，每个声明是否支持幂等查询，不支持的进人工核对队列。

前端十页：登录/SSO、咨询台、工单进度、客服台、审批台、知识与发布、运行诊断、用量与账单、组织与成员、审计导出。每页必须表达当前状态、下一步、失败原因、责任方。
