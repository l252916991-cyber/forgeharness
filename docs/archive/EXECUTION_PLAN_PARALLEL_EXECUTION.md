# 有界并行执行计划书

日期：2026-10-27。基线：ForgeHarness SDK 0.8.6 / API v1。
状态：**P0–P4 的实现与开发验证已接入，P5/P6 的正式证据读取执行报告**。
本计划保留原验收要求；接口与实现详见 [并行接入说明](../guides/PARALLEL_EXECUTION.md)，
实际候选资格及性能结论详见 [执行报告](../../reports/parallel-execution-20261027/REPORT.md)。
实施继续使用 Python 3.12、uv 和框架无关的核心。

## 1. 决策与目标

将有界并行列为下一阶段优先事项：让同一任务中没有依赖关系的专家同时处理材料，
在结果完整且校验通过后再综合。第一阶段验收两个模型请求并发，保留串行配置作为
兼容入口和性能对照。并行基础设施的实现不以多角色提高回答质量为前置条件；
是否在某个业务和模型配置上推荐开启，由该配置的正确性、资源和性能证据决定。

典型交付流程：资料与权限快照 → 两名专家同时分析 → 分别校验、记账 → 协调者综合。
三名以上专家按容量分批执行，不能以专家数量直接决定同时发送的请求数量。
依赖链仍按依赖运行，公共目标与各专家私有材料继续遵循现有可见性边界。

本计划交付两项分别报告的结果：

- **机制合格**：确实存在请求重叠，并发上限、预算、权限、trace、取消和恢复可靠。
- **目标配置收益**：相同拓扑在指定模型与机器上的时延改善，有完整质量和资源对照。

现有 0.8.6 候选的 95/95 门禁、1262 项测试属于
[历史冻结候选](../../reports/multi-agent-20261026/REPORT.md)，不能认证后续并行实现。
旧 [A/B/C 实验](../guides/STRATEGY_COMPARISON.md)改变了编排策略且调用全部串行，不能证明
并行有效或无效。本计划独立冻结协议与证据，不覆盖原实验。

## 4. 调度与持久化设计

### 4.1 一个 owner 提交状态，多个 worker 等待响应

owner 串行负责校验、就绪选择、容量获取、预算准入、checkpoint、schema 校验、
结算和下游调度。worker 只接收不可变调用票据，执行一次模型请求并返回结构化事件；
不能修改 runner.state、current_node、根 messages 或数据库。

票据至少包含 run/node/invocation 身份、owner 代次、规范请求摘要、模型配置身份和
节点预算。结果必须匹配票据；过期 owner、重复或冲突结果不能覆盖当前状态。
每个调用的上下文独立，不能依赖一个跨 await 的共享 current_node 指示所属任务。

就绪节点按图中定义顺序选择；完成事件按实际到达顺序持久化。综合输入始终按声明的
依赖顺序构造。可重建的是确切输入、调度决策和状态转换，不承诺并发时每次的墙钟
完成顺序一致。对于额度紧张的图，准入/等待决定也必须留证据。

### 4.2 发送边界先落盘

| 阶段 | 必须完成的动作 | 崩溃后的处理 |
|---|---|---|
| 就绪/等待容量 | 检查依赖；排入有界队列；尚未进入 provider | 重建队列并重新检查权限、截止时间与容量 |
| 已预留、未发送 | 原子预留预算；准备规范请求；保存输入身份 | 仅在可证明尚未跨越发送边界时重新准备/发送 |
| 发送许可已持久化 | 保存精确 prepared request、调用身份与发送标记，trace 写入获确认 | 即使不确定是否真的发出，也按 unknown 保守处理 |
| 响应已收到、未提交 | 校验票据、结果和用量，准备原子结算 | 查询已有回执或保留 unknown；不得重新推理 |
| 已结算 | 节点、预算、checkpoint、outbox 一次提交 | 复用结果；重复交付不重复扣费或触发下游 |

新协议需区分“本 owner 正在等待”与“响应/用量需要对账”，展示状态不能误导用户。
P0 确定持久 schema/recovery 版本和迁移拒绝规则，形成 ADR；不将旧状态直接解释为
新协议。已跨越发送边界且结果未知的调用，恢复只查询已有回执或进入对账，不重新
推理；可证明尚未发送的调用经重新校验后允许执行。只读、幂等或超时不能授权重发
未知模型请求。

### 4.3 模型适配器与 trace

模型适配器必须明确支持并发，或由工厂为各调用创建隔离实例。HTTP 连接池可以按其
契约复用，角色 messages、用量、缓存和请求 ID 不能跨节点串用。不能假设现有所有
model_factory 返回值都可并发；未声明支持的适配器使用串行或在配置时明确拒绝。

每个 run 只有一个 trace writer；事件包含 node_id、invocation_id 和 owner 代次。
worker 提交的请求事件必须收到持久化确认后才能发送；状态 outbox 可重放且可去重。
事件队列有容量和背压，磁盘写入失败停止新准入；不能静默丢弃模型可见输入或结果。
权限撤销后禁止返回敏感输出，但内部受限审计仍须保留必要用量、回执和来源身份，
不能因对外访问被拒绝而忘记已经发生的消耗。沿用凭据过滤和私有状态目录要求。

## 5. 预算与 provider 容量

### 5.1 根预算只有一本账

沿用当前 `_admit()` 的逐维占用规则：在途或 unknown 节点按
`max(已知用量, reservation)` 占用，已结算节点按实际用量占用。准入时要求：

```text
所有节点当前占用之和 + 新节点最大用量 <= 根预算
```

步骤、工具次数、输入/输出 tokens 等各维度分别比较；未知节点的已知步骤与完整
预留不能简单相加重复计算。检查、预留、持久化由 owner 一次完成，不能让多个 worker
分别看到同一份剩余额度。Collaboration 构造时的总声明预算检查继续保留。

已知实际消耗即使超出声明也要如实记录，并停止新准入、标记失败。结构化结果无效
同样保留实际消耗。unknown 保留保守预留；恢复、取消、超时和重试都不能重置预算。
首期不增加模型自动重试；明确未发送的本地准备失败才可以释放相应未发生的预留。

### 5.2 run 上限与 provider 上限分开

| 控制 | 作用与边界 |
|---|---|
| run 并发上限 | 同一 run 最多 1 或 2 个模型请求在途 |
| provider 总容量 | 同一受管 provider 的所有 run 共享容量，首轮测量上限为 2 |
| 等待队列 | 有界排队、明确满载结果；跨 run 公平轮转，每轮最多取得一个新槽位 |
| 资源准入 | 本地模型检查目标上下文长度和动态内存；不合格时保存诊断并停止加压 |

获取容量期间 owner 仍须处理已完成结果、取消和截止时间，不能等待一个 semaphore
而阻塞整个结果提交循环。发送前再次检查当前授权、身份和期限；准备失败释放未使用
容量。预算预留与容量登记的故障窗口须逐一验收，不能长期占着一个资源等待另一个。

首期容量保证限于同一 dispatcher 管理的调用。通过容量域配置与排他锁阻止本项目
第二个 dispatcher 未经协调地复用同一域；多进程/多机共享 provider 需另行共享协调。
外部客户端不在此保证内，应使用独占评测实例或 provider 自身的限制。
普通 asyncio 同步原语也不提供线程级同步，不能据此声称实现宿主全局限流。
参见 [Python 3.12 同步原语](https://docs.python.org/3.12/library/asyncio-sync.html)。

请求断连不证明后端已经停止推理。预算预留和物理容量的释放条件分别记录：能确认
调用已结束时可释放容量，消耗未知时仍保留预算。dispatcher 重启后加载未决发送记录；
无法确认后端在途量时暂停该容量域的新发送，完成对账或确认后端已清空后再恢复。
不能靠 TTL 到期或本地协程退出自动认定远端工作消失。

## 6. 失败、取消和恢复

一个分支失败后停止新准入，已在途分支继续有界收尾并记录已知结果；依赖失败分支的
协调者不得执行。取消与 deadline 也先阻止新发送，再收尾在途调用。收尾时限和 provider
超时进入配置及 trace；超过收尾时限但无法确认的调用持久为 unknown。

Python TaskGroup 默认会因子任务异常取消其他任务，因此预期的节点失败应转成明确
结果事件，再由调度器实施上述规则；编程错误与外部取消也须经过清理和未知状态登记，
不能直接退出后释放所有预留。[Python 3.12 TaskGroup 文档](https://docs.python.org/3.12/library/asyncio-task.html#task-groups)

| 场景 | 必须保持的结果 |
|---|---|
| 一成功、一失败 | 成功结果和两者已知用量保留；综合不执行 |
| 一成功、一 unknown | 成功结果复用；未知节点只对账，根状态明确需要对账 |
| 取消与响应同时到达 | 响应可结算，但不触发新下游；取消不抹掉实际消耗 |
| 运行中撤权/材料变化 | 停止新发送和对外暴露；在途消耗仍可在受限账本结算 |
| owner 崩溃、两个请求在途 | 恢复时分别判定；已完成不重跑，未知不重发 |
| 旧 owner 迟到响应 | 不得直接写入新状态；只能经当前 owner 验证回执后按对账规则接纳 |
| 活 owner 挂起 | 沿用 OS 锁，不通过过期租约强行夺取活 owner |

run 退出前回收本地 worker、定时器、连接和队列；有未决远端工作时保留可查询状态。
“取消已请求”“本地等待已结束”“后端已确认停止”“用量已对账”应分别呈现。

## 8. 无模型验收矩阵

测试使用 scripted provider、可控事件屏障、故障注入和新进程恢复。时间上限仅用于
防止测试挂死；用事件与持久证据断言并发，不用短暂 sleep 或脆弱的秒数阈值证明。

| 类别 | 最低场景 | 硬性判据 |
|---|---|---|
| 真实重叠 | 两节点均进入 provider 后才允许任何一个返回 | 配置 2 时峰值在途 2；配置 1 时峰值 1 |
| 容量与公平性 | 三节点/两槽、两个 run 共用 provider、队列满、工具屏障 | 不超各层上限；第三节点等待；无饥饿/死锁；工具无同 run 重叠 |
| 依赖与隔离 | 正序/逆序完成、不同私有证据、共享适配器拒绝或隔离 | 综合不提前；其输入顺序固定；节点间不串材料/消息/用量 |
| 预算 | 争抢最后额度、精确边界、已知部分用量、超声明用量 | 零超额准入；占用不重复；实际超量保留并失败 |
| 结果校验 | 非 JSON、越界引用、非法工具 action、错误 schema、对账结果 | 一致拒绝；已发生费用计入；下游不接收非法输出 |
| 中断与撤权 | 取消/超时/撤权与返回交错、一个失败另一个尚未返回 | 停止新准入；已知结果只结算一次；未知保留预留 |
| 崩溃窗口 | 预留后未发送、发送标记后、收到响应未提交、提交后 outbox 未确认 | 已发送未知不重试；已完成不重跑；outbox 可重放去重 |
| 恢复与 fencing | 两在途节点进程退出、两个恢复进程、迟到/重复/冲突回执 | 一个 owner；旧写入被拒；每节点至多一次结算与下游触发 |
| trace 与磁盘 | 乱序事件、写失败、背压、重启追加 | 序列与 hash 链可验证；发送前请求已落盘；无静默丢失 |
| provider 故障 | 429/507/超时、usage 缺失、容量等待中取消、dispatcher 重启 | 按证据分类；未知不释放成可免费重试；未决容量不被遗忘 |

覆盖入口以现有 [durable 测试](../../tests/unit/test_durable_orchestration.py)、
[collaboration 测试](../../tests/unit/test_collaboration.py)、
[model_call 测试](../../tests/unit/test_model_call.py)为基础。现有名称包含 parallel 的审批测试
和角色顺序测试都不能替代真实重叠测试。新增测试文件及故障脚本在 P1–P3 交付。

## 9. 真实模型评测协议

### 9.1 对照与样本

只改变并发配置 1 与 2；保持相同拓扑、角色提示词、证据快照、模型文件/配置、
节点预算、根预算和 grader。两个配置必须调用相同节点，不用减少模型调用制造提速。
温度与 seed 在后端支持时固定，但不能假设温度 0 保证输出逐字一致。

建议开发集 12 题，评价集 30 题，每题每配置 3 次，共 180 次根运行。三个任务族各
10 题：两个独立专家、依赖链控制、耗时不均的独立分支；链式控制使用普通 R2 图。
每题重复样本按 task 聚类，不能当成 90 个独立任务。作者自建样本披露其局限；
真实业务上线还需独立材料和领域评分，不以结构化输出合法代替结论正确。

开发阶段确定资源和评分方法后封存终评协议：绑定源码摘要、runner、数据集、模型、
阈值、样本数与执行顺序。对照顺序按预登记 seed 交替/随机，记录缓存、预热和桌面负载；
不能看过正式结果后换阈值或挑样本。旧 strategy runner 不自动适用，P5 交付专用 runner。

### 9.2 指标与判定

| 指标 | 记录或建议门槛（P5 开发阶段后、终评前封存） |
|---|---|
| 请求重叠 | 每节点准入/发送/结束时间、峰值在途、等待 provider 容量时间 |
| 端到端时延 | 可并行任务族 p50 ≤ 串行 0.80 倍、p95 ≤ 1.10 倍；链式控制单独报告开销 |
| 质量 | 配对 task 聚类 95% 区间中，成功率差下界 ≥ −5 个百分点；严重错误单列 |
| 实际消耗 | 总 input/output tokens、失败消耗、每成功任务 tokens；后者 ≤ 串行 1.10 倍 |
| 资源与稳定性 | 统一内存、swap 增量、吞吐、429/507/超时、unknown 和人工对账次数 |
| 可追溯性 | 所有尝试、失败、中断、回执和协议摘要完整；缺失样本不能当作成功或零耗时 |

失败计入尝试分母；同时报告全部尝试的耗时分布和成功任务的配对耗时，防止快速失败
造成虚假提速。未结束请求标记未决/截尾，不能把停止等待的时间当成完成时间。
基础设施故障保存原始证据，该批结论不合格，修复后使用新批次；不覆盖失败历史。
样本量不足以支持质量区间时报告“不确定”，不能用点估计代替非劣性证据。

受控延迟的假 provider 只验证 harness 重叠；真实 HTTP 请求重叠也不自动证明模型
服务内部同时推理。服务端可能排队、批处理或受到内存/带宽限制，服务端无法观测时
明确记录“内部调度未知”。首轮使用独占时段测本机并发 2，不预先承诺两倍速度。

历史环境为 M4 Pro / 48 GiB、oMLX 0.7.0 与本地 27B 模型，仅作为校准起点；
实际运行前重新记录硬件、软件、权重摘要、上下文长度和可用内存。历史有 HTTP 507，
不能用总内存容量推断目标并发必然可承受。资源不足立即停止加压并保留诊断。

若机制合格而目标后端性能未达标，可交付显式可选的并行能力，但该配置继续推荐
并发 1，报告不能写“并行性能验收通过”。并发 2 的生产推荐需性能与质量条件同时满足。
换模型、机器或后端批处理配置后重新校准；并发 4 放入后续独立协议。

## 10. 发行、回退与模型资源

实施报告建议放入新的 `reports/parallel-execution-<实际执行日期>/`，分开保存设计审查、
keyless 证据、开发评测、封存协议、正式评测、候选与最终报告。目录名不复用旧报告，
候选编号递增，修复必须冻结新候选并重新验证。

P5 正式采样前冻结评测源码；P6 发行冻结必须校验同一相关实现身份。若之后改动调度、
模型请求、预算、评分或数据，重新封存并重跑受影响的正式评测，不能沿用旧性能数字。
仅文档等无关变更也要列出差异、说明影响，并对最终候选重跑全工程门禁。

复用 [候选验证器](../../benchmarks/comparison/verify.py)与
[干净副本验证](../../benchmarks/verify_clean_candidate.py)：格式、静态/类型、完整测试、
分支覆盖、故障评测、依赖审计、wheel/sdist、最小安装及示例全部通过。新增并行验收
接入门禁；95 是旧候选门禁数，不限定新门禁数。检查架构、正确性、安全边界、依赖、
文档和恢复声明，所有发现分级，blocker/high 修复并补回归，记录接受的残余风险。

发行时同步 [CI](../../.github/workflows/ci.yml)候选路径和当前能力文档；现有 CI 仍引用
较早的 improvement 候选，不能拿该路径认证新源码。当前工作区无 Git 元数据，继续
使用已验证的 archive checkout-equivalent 冻结方式，不能假定有可用 worktree。

出现性能退化时，新 run 可使用并发 1；活动 run 保持其绑定配置完成或取消/对账，
不能通过修改配置重解释已有发送记录。旧版运行由旧 wheel 收尾；不提供隐式原地降级。

模型资源执行规则：

1. 计划、编码、屏障测试、故障注入和工程门禁使用 scripted 模型，本地推理服务保持停止。
2. 只有 P5 真实评测需要推理；启动前核对既有进程、端口与资源，记录本次进程归属。
3. 评测完成、失败退出或资源不足后，停止本次启动且确认归属的服务，验证进程和端口
   已释放；保留模型权重与报告，不停止其他任务正在使用的服务。
4. 工程门禁通过不表示真实模型评测已完成；完整项目也不因本期并行交付而自动完成。
