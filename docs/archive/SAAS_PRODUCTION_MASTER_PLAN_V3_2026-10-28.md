本计划响应最新目标：将 ForgeHarness 发展为可向多个组织持续交付、运营和收费的通用 Agent SaaS 平台。它是后续总体路线；单租户试点是获得业务证据的中间里程碑。本文不表示已启动云资源采购、真实收费或生产发布。

## 1. 最终交付与范围

最终交付包括三个相互配合的部分：

1. **ForgeHarness SDK**：应用中立的执行、权限、预算、审批、状态恢复与证据核心。
2. **ForgeHarness Cloud**：组织与工作空间、托管执行、应用发布、连接器、密钥、用量、账单、可靠性和运营控制面。
3. **应用包**：电商咨询/人工服务与内部知识问答/审批作为两个跨业务验收样例；首个真实试点业务后续确定，两者均使用相同核心和平台契约。

“通用”验收为：第二个业务应用能通过受支持的工具、策略、资料、输出与评测契约接入，核心不出现电商或客户特判。GA 提供租户级 API、SDK 示例和受审核的应用包发布；任意第三方插件市场、任意用户代码执行属于后续独立等级。

“生产级”验收为：真实账户和资料可以持续使用，隔离、成本、故障恢复、升级、值班及客户支持均有实测证据和责任人。技术质量、业务效果、商业运营分别签收。

默认产品假设：面向需要受控 Agent 执行的企业团队；采用组织订阅加额度/超额计量；以一个云和一个主区域起步，GA 在主区域多可用区部署。地区、规模、预算和已有资源以试点范围为准；实际云区域、支付渠道和负责人仍待 M0 冻结。

共享资源、专属资源和混合部署都可属于 SaaS；本计划默认共享控制面、共享执行池，保留同源专属池能力。关键是统一开通、版本、配置和运营，专属实例不是另开客户分支。[AWS SaaS 架构模型](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)

## 3. 对旧计划的修订

| 旧稿问题 | v3 的处理 |
| --- | --- |

| 要求所有租户始终同一个 digest | 正式发布有统一版本谱系，允许灰度和旧运行保留旧镜像；差异可追溯 |
| 将专属实例排除在 SaaS 外 | 允许共享、专属、混合隔离；统一控制面和生命周期 |

| 将零保留、每租户密钥和 30 天备份硬删一律设为事实 | 改为按数据类别和合同选择；删除必须覆盖实际所有副本和密钥路径 |
| 强制发生一次真实事故才能验收 | 可控故障演练验证处置，真实事故如实记录，不制造客户事故 |
| 对账同时要求零漂移和允许 0.5% | 内部计量必须精确；外部差异进入待核对，不用容忍率掩盖错账 |
| 默认失败后自动换模型重试 | 只在数据授权、质量、预算和调用结果允许时降级；未知副作用先核对 |
| 人日与日历周期不一致 | 统一有效人日、风险缓冲、团队效率和观察窗口计算 |

本文提出的是本产品的验收标准，不将其冒充所有 SaaS 的普遍定义。

## 5. 目标架构与所有权

```text
浏览器 / 企业系统 / API 客户端
          │ HTTPS + 身份 + 请求限流
          ▼
控制面 API：组织、应用发布、运行受理、审批、资料、计费与管理
          │ 单事务：run + 请求幂等 + 调度 outbox
          ▼
PostgreSQL ───────► 调度器 / 队列 ───────► 执行 Worker
  │ 权威状态          │ 可重建通知           │ 租约 / epoch / 当前权限
  │ 预算与回执        │ 公平派发             ├─ Harness 执行
  │ 计量与审计        │                     ├─ 模型网关 → 已授权 provider
  │                                        └─ 工具网关 → 已授权业务系统
  └─ 证据清单 → 私有对象存储（资料、输入、输出、trace、附件）

独立能力：IdP、密钥托管、观测告警、账单渠道、灾备与发布流水线
```

初期采用模块化应用、API 与 worker 独立进程。只按信任边界和资源需求拆进程，暂不要求每个模块独立微服务。容器服务须支持滚动发布、多 AZ 与隔离网络；是否采用 Kubernetes 在 M0 按运维能力选择。

| 对象 | 唯一事实来源/写入责任 | 故障时处理 |
| --- | --- | --- |
| 账户、成员、角色、应用版本 | 平台 PG，身份/发布服务 | 无法重验授权时拒绝敏感操作 |
| run、checkpoint、approval、预算、调用回执 | PG，经过事务的运行状态仓储 | 暂停接管/发送，不能由缓存推断状态 |
| 队列消息、Redis 缓存 | 调度提示和派生数据 | 可由 PG 扫描重建，丢消息不丢已接受任务 |
| 工具副作用 | 外部业务系统，本地保存请求及回执关联 | 原业务键查询；不可判定则等待对账 |
| 模型调用用量 | 实际观测记录和 provider 回执 | unknown 保留，不能自动记零 |
| 资料/完整执行证据 | 对象存储内容 + PG 摘要/版本清单 | 引用缺失使证据状态失败，不假装可重放 |
| 用量、计价、账单 | 追加事件与版本化账本 | 重放聚合；更正用反向/调整分录 |

Redis 锁、队列可见性超时和 worker 进程存活均不能独立决定谁有执行权。PG 与对象存储无法共享一个本地事务，采用不可变对象、摘要引用和提交状态协议；未提交孤儿对象可回收，已引用缺失对象必须报警。

## 6. 组织、账户与授权（W1）

### 6.1 产品功能

- 组织创建/邀请/接受/退出/停用；用户可加入多个组织，切换组织时重新绑定当前上下文。
- 工作空间、成员、角色、服务账号、API Key 创建/轮换/撤销、最近使用记录。
- Owner、组织管理员、开发者、操作员、审批人、财务、审计员分别授权；平台运维不默认读取客户内容。
- 使用标准 IdP 处理登录、密码恢复、MFA；企业联合登录和 SCIM 分别作为独立能力验收。
- 浏览器会话提供安全 Cookie、CSRF 防护、绝对/闲置过期；组织禁用和成员撤权作用于下一次受保护请求及副作用发送前检查。
- 密钥、付款方式变更、敏感导出、重要审批按策略要求再次认证；紧急支持访问限定对象/时限/原因，并向租户留下审计。

### 6.2 接入设计与验收

复用已有 IdentityStore 的领域授权语义，先验证并抽出应用中立接口；密码迁移可以使用邀请重置或有截止日期的兼容路径，不直接删旧凭据让用户失去访问。

登录身份以 issuer + subject 绑定，不仅凭邮箱关联账户。采用 OIDC 授权码流程和 PKCE，校验 issuer、audience、签名、有效期、重定向地址及流程绑定；组织角色由平台授权数据提供。[OIDC 规范](https://openid.net/specs/openid-connect-core-1_0.html)、[OAuth 安全建议](https://www.rfc-editor.org/rfc/rfc9700.html)

验收：同角色两人仍是两个主体；伪造组织参数、过期邀请、被撤销 API Key、自批、用户转组织、连接池复用和后台任务访问均有拒绝测试。撤权传播目标在 M0 冻结；外部 IdP 的禁用事件到达延迟与平台内部禁用分别测量。

## 7. 租户隔离与数据契约（W1/W2）

租户由组织定义；workspace 是组织内的子范围。每个业务对象带 org_id，关联对象使用包含 org_id 的外键/唯一约束，避免 ID 正确但所属租户错误。

| 对象组 | 关键实体 | 需要的约束 |
| --- | --- | --- |
| 身份 | organizations、users、memberships、service_accounts | 组织内成员身份唯一、撤销版本明确 |
| 应用 | applications、deployments、versions、policies | 已发布版本不可变、环境与授权清晰 |
| 执行 | runs、nodes、attempts、leases、approvals、receipts | run/节点/尝试唯一，epoch 和状态条件更新 |
| 业务 | sessions、messages、tickets、knowledge_revisions | 所属主体/组织/来源和业务幂等键明确 |
| 证据 | audit_events、trace_manifests、artifacts | 按组织授权、内容摘要、提交/保留状态 |
| 财务 | usage_events、reservations、ledger_entries、invoices | 重复事件不重复计费，币种/计量单位/版本明确 |

应用仓储必须接收可信租户上下文；不设默认租户。PG RLS 作为第二道约束：应用角色不能是超级用户、BYPASSRLS 或表所有者；需要时 FORCE RLS；读与写策略都要验证。事务内设置租户上下文，连接归池后不得串租户。RLS 对特权角色存在绕过边界，不能取代应用授权。[PostgreSQL RLS 文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

隔离测试覆盖所有租户接口及后台入口，不固定为“只测 12 个端点”。包含分页/搜索、缓存、全文/向量检索、导出、对象下载、消息订阅、任务恢复、账单、日志查询、运维后台和删除任务。分别验证组织间、工作空间间、同组织不同成员权限。

对象存储使用私有桶及授权下载；短期签名链接不是默认一次性凭证，需要单次消费时增加服务端令牌。网络地址、重定向和 DNS 解析均需出口校验，防止连接器访问元数据地址或未授权内网。

## 8. 存储、跨机恢复与迁移（W2）

### 8.1 必须迁移的完整状态面

SDK session、task、checkpoint、approval、invocation journal、R2 graph、预算预留、provider 容量、outbox、删除墓碑和 trace 清单均需纳入。只迁 session 表不能支持跨机接管。

定义操作级存储契约：原子受理、审批消费与调用准入、预算预留/结算、epoch 条件提交、完成/失败/unknown 记录。不要让“通用 CRUD 接口”拆散原本必须原子完成的事务。

SQLite 适配器继续支持本地 SDK；PG 实现通过同一契约测试，并增加真实 PG 的事务冲突、重试、死锁、权限和断连测试。平台后端与本地后端各自声明支持范围。

### 8.2 稳定身份

新 SaaS 运行以 tenant / deployment / run / node / attempt / provider-account 等逻辑身份绑定；物理机器和绝对目录不再决定恢复身份。配置版本、模型和工具契约仍属于运行身份。旧 0.9.2 身份保留原约束，不篡改旧 checkpoint 以伪装兼容。

### 8.3 切换流程

1. 盘点状态文件、schema、活跃审批、未知调用、待发送 outbox 与业务回执；固定版本和快照。
2. 在独立目标环境转换副本，核对行数、业务键、摘要、审批与用量，不发出外部写入。
3. 优先迁静态配置和已结束运行；活跃运行由旧版本排空。必须迁活跃运行时单独冻结迁移协议和恢复测试。
4. 切换时停止准入和写者，备份并执行最终校验，再打开新环境。禁止 SQLite/PG 长期双主双写。
5. 新环境开始写入后，旧数据库不能直接重新接管；回退应用版本仅在 schema 兼容时允许，数据回退需有经过演练的反向迁移/重放方案。

验收：审批、预算、unknown 和已完成副作用跨进程/跨节点保持一致；迁移失败可停在可解释状态；保留已删对象墓碑和回执，避免恢复后重复执行。

## 9. 分布式执行与副作用（W3）

### 9.1 受理和运行

API 完成身份、输入、额度和幂等校验后，同事务写 run 与调度 outbox，返回 202 + run_id。业务意图的幂等键由客户端生成并保存；重复相同 payload 返回原 run，修改 payload 使用同键返回冲突。

worker 竞争租约并取得单调递增 epoch。每个状态更新、预算结算、证据提交都检查 epoch 与预期状态；过期 worker 不能结算旧结果。任务超时、取消和审批等待均有持久状态，不依赖 Web 连接存活。

集群多 worker 与单 run 内模型并行是不同维度。平台先扩大独立 run 的吞吐；单 run 并发沿用已验证的 1/2 配置，并对新存储后端复验。

### 9.2 状态与未知结果

运行可处于 queued、running、awaiting_approval、cancelling、reconciling、succeeded、failed、cancelled、exhausted；pending/unknown/confirmed 同时记录在具体调用上。HTTP 成功响应只说明 API 操作成功，不能直接表示业务完成。

用户可取消 queued run；运行中先持久化取消请求并阻止新调用，再等待在途结果。已发生业务写入仍保留回执；必要的补偿是独立受授权操作。

### 9.3 发送边界

外部服务未必识别 fencing token：本地 epoch 不能自动阻止已发出的请求。每个连接器必须声明幂等、查询、取消与回执保留能力。发送前记录调用标识和预算预留；超时、失联、owner 丢失后，按原标识核对，无法判定则转人工。

任务终态必须等待所有影响结果的副作用得到确认或准确失败分类。Outbox 提供至少一次投递，不能据此宣称外部 exactly-once。

### 9.4 配额与公平

配额覆盖 run、用户、租户、provider 账号和平台；含模型并发、token/金额预算、队列长度、存储与请求速率。关键预算在权威存储原子预留，Redis 只用于快速预检。隔离不同 provider-account 的限流域，同一共享账号的全局上限跨 worker 生效。

采用按租户轮转/权重和队列年龄保护，允许有上限的突发，配置按套餐版本记录。Redis 丢失、重复消息、毒消息、长时间审批和单租户洪峰不得造成其他租户无限等待。

验收重点：暂停旧 worker 后接管，再恢复旧 worker；审批并发消费；同键并发提交；模型已发出但丢响应；队列重复/丢失；数据库切换；租户撤权与取消发生在发送前后。

## 10. 模型、工具和应用版本（W4/W5/W9）

### 10.1 模型网关

- 管理租户可用模型、provider 账号、模型配置、实际 usage、token/金额预留和队列。
- 每次运行固定模型配置、提示词、工具和策略版本，保留实际发送请求的可核验证据。
- 重试进入同一预算账本；模型切换按租户数据区域、授权和质量验证选择，用户可看出降级。
- 平台托管凭据与 BYOK 分开，凭据以 secret_ref 注入；工具结果和 trace 均不得携带明文密钥。
- 格式验证与业务验证分层；结构合法不代表事实正确，来源存在不代表支持结论。
- 注入检测是辅助措施，授权、工具 allowlist、数据范围和独立审批持续由代码执行。

### 10.2 连接器契约

每个连接器声明：权限、出站域名、读写副作用类型、超时、重试条件、业务幂等键、回执查询、输入输出 schema、版本兼容、撤权与删除能力。发布前运行契约和故障矩阵。

读连接器提供当前值/版本/时间；写连接器提供执行结果及核对接口。没有取消能力就明确显示“无法撤回”，不能统一伪造 cancel 成功。

GA 默认执行平台审核的工具与应用包。后续开放用户代码前，需独立容器/微虚拟机隔离、无默认网络、CPU/内存/时间/磁盘限制、短期凭据与逃逸测试；路径限制不能充当系统沙箱。

### 10.3 应用发布与开发者体验

应用有草稿、验证、已发布、停用版本；定义配置 schema、工具、策略、输出、预算、评测集和兼容 SDK。按组织配置应用，不复制核心。提供版本化 OpenAPI、SDK 示例、分页、幂等、错误码、重试提示、事件订阅和签名 webhook；公开弃用窗口。

GA 第二应用建议内部知识问答与审批草稿。其接入只修改应用包和适配器，并在同一平台验证租户、权限、引用、预算、审批、审计、计费和恢复。

## 11. 用户产品与首个业务闭环（W5/W6）

| 工作台 | 必须可完成的任务 | 验收重点 |
| --- | --- | --- |
| 开通与组织 | 验证账户、建立组织、邀请成员、选应用 | 独立用户无需开发者代操作 |
| 咨询/任务 | 新建、历史、来源、进度、取消、结果 | 刷新断线复用 run；状态清楚 |
| 审批 | 对象/参数/风险、批准、拒绝、到期 | 独立身份、批准内容绑定、变更失效 |
| 人工服务 | 创建、领取、处理、解决、重开、查看进度 | 并发领取只有一人成功，用户只看有权工单 |
| 知识 | 上传、失败原因、编辑、审核、发布、撤回 | 历史版本与当前有效性分开、影响面可查 |
| 应用/连接 | 环境配置、工具权限、密钥状态、发布 | 秘密不可回显、发布可追溯 |
| 用量与费用 | 额度、预留/未知用量、账单、付款状态 | 所有收费行可解释、超额提醒 |
| 管理与审计 | 成员、角色、API Key、导出、支持工单 | 高权限操作留证、支持访问透明 |

前端同时验证键盘操作、焦点、表单错误、时间/金额格式、加载/空态/失败态和移动端基本适配。身份令牌、trace 内部结构与框架术语只在确有用途的诊断界面展示。

电商主链路：授权查询 → 当前来源回答/澄清 → 用户请求人工 → 独立审批 → 单张工单 → 客服领取 → 处理结果 → 用户查看。价格库存以业务工具为准；真实数据未提供时，测试数据显式标注，不能形成真实试点合格结论。

知识主链路：文件校验与解析 → 租户隔离索引 → 来源定位 → 审核发布 → 引用回答 → 撤回与缓存失效。文件类型、大小、解压/解析资源、恶意内容、附件下载及删除传播都有独立测试。

## 12. 计量、收费与运营（W7）

### 12.1 三种数值各司其职

| 数据 | 用途 | 规则 |
| --- | --- | --- |
| 预留额度 | 调用准入、防止并发超卖 | 未知用量不自动释放；可人工核对 |
| 实际供应商用量/成本 | 成本核算 | 按每次物理调用记录，失败和重试计入 |
| 客户应付金额 | 商业合同结算 | 按套餐与计价版本，不能直接等同 provider 成本 |

路径：usage event → 幂等追加账本 → 套餐聚合 → 草稿账单 → 核对 → 出账 → 支付/欠款/退款与调整。金额用明确精度的十进制或最小货币单位，禁止浮点直接累计。

事件含 org、run、attempt、event_id、计量单位、发生/接收时间、来源和修正关系。迟到用量、重复事件、跨月归属、时区、取消、部分失败、免费额度、套餐升级和退款都须有规则。

支付回调验证签名与时间，处理重复和乱序；事件先可靠保存再响应，业务侧幂等更新，必要时向支付方读取当前状态。Stripe 文档可作为这种回调契约的参考，具体支付渠道仍取决于运营地区。[支付 webhook 文档](https://docs.stripe.com/webhooks)

### 12.2 验收与商业配置

- 内部事件到账本与聚合精确一致；重放不产生额外费用。
- 外部账单对账区分延迟、币种、缓存 token、折扣和舍入；所有未解释差异阻断受影响行项出账，已知小额舍入只在事先冻结规则内处理。
- 先跑影子计费，再验证沙箱支付全生命周期，最后经商业授权执行实际小额收费/退款及真实账期对账。
- 套餐默认 Trial、Team、Business；额度、超额开关、保留期限、服务支持可配置。Enterprise 根据专项能力另行签收。
- 免费试用有总额上限、注册/密钥滥用防护和禁用流程。欠费先停止新增消耗，按合同保留查账、导出和数据处置通道。
- 管理后台支持账单争议、有限额度调整、租户停用/恢复、订阅变更、通知失败重投及客户支持。

不预设支付商、币种、税率或固定价格。选择运营主体和客户地区后，核对支付覆盖、开票、合同和适用义务；未调查时不默认全球经营能力。

## 13. 可靠性、容量和灾备（W8）

以下为规划提案，M0 按环境与客户需求定版。验收前固定口径，失败后不得临时放宽门槛。

### 13.1 SLO 与测量

| 指标 | GA 初始提案 | 测量边界 |
| --- | --- | --- |
| 控制面可用性 | 滚动 30 天 ≥99.9% | 好请求/有效请求；包括超时、错误及容量不足，合法权限拒绝单列 |
| 受理与状态查询 | p95 ≤500 ms | 在冻结负载下，不包含模型生成，包含 API 内部依赖 |
| 队列等待 | p95 ≤5 秒 | 在承诺额度和设计负载内；过载拒绝单列，不剔除掩盖 |
| 整任务时延 | 按应用/任务族设目标 | 用户等待时间包含排队和依赖；人工审批时间另报 |
| 运行可靠性 | 系统原因失败率 ≤1% | 权限拒绝、业务拒绝、unknown、取消分别计数；超期未完不能被移出分母 |
| 业务效果 | 每应用独立契约 | 引用范围、事实正确、转人工及任务成功各有分母 |

同时看租户和平台 SLI，避免大租户平均数掩盖小租户故障；无用户流量时用外部合成探针补充。真实 provider 与桩测试分别出报告。内部 SLO 与合同 SLA 分开，合同承诺需观测、值班和商业条款支持。[Google SRE 的 SLO 方法](https://sre.google/workbook/implementing-slos/)

### 13.2 容量提案

初始测量设计点：300 个配置租户、3,000 月活用户、30,000 run/日；并发活跃会话、执行中的 run、模型 HTTP 调用、token 吞吐分别记录。

估算例：峰值一小时占全天 20%，则峰值约 1.67 run/s；平均 3 次模型调用、每次 6 秒，则模型占用约 30 个并发请求。规划可用并发 60 是容量假设，必须同时通过 provider RPM/TPM、token 长度分布及实际服务延迟验证。

压测：设计点持续 24 小时、2 倍峰值至少 60 分钟、单租户突发、慢模型/大文件、审批积压与欠费租户。其他正常租户 p95 劣化 ≤20% 且仍满足目标作为初始噪声邻居门槛；硬预算不突破、无无限等待和无未解释丢失。超过设计点须可预测限流和告警。

### 13.3 灾备分层

| 故障 | GA 提案 | 实测覆盖 |
| --- | --- | --- |
| 单 API/worker 故障 | 2 分钟内完成可安全接管任务的恢复 | unknown 调用可继续对账，不能强迫重发 |
| 单 AZ 故障 | RTO ≤15 分钟；已确认 DB 事务目标 RPO=0 | 受数据库同步与故障条件约束，同时检查对象证据 |
| 数据误删/单租户恢复 | RTO ≤4 小时，目标恢复点 ≤5 分钟 | 隔离 PITR → 按租户核验回灌 → 副作用/墓碑检查 |
| 整个主区域不可用 | GA 冷恢复 RTO ≤24 小时、RPO ≤24 小时 | 异地/独立故障域备份须被数据驻留政策允许 |
| 企业级区域切换 | 可选 RTO ≤1 小时、RPO ≤5 分钟 | 额外复制、备用容量、控制面/IdP/密钥可用性及演练 |

RTO 从检测到故障起，直到身份、读写、执行和关键结果均可用；RPO 按实际可恢复提交点核对。只恢复数据库不算恢复完成；证据对象、密钥、部署配置、计费和外部回执一起核验。区域故障目标与主区域正常服务 SLO 是不同维度，SLA 如实说明覆盖范围。

### 13.4 值班和运行手册

告警覆盖错误预算燃烧、排队、DB/对象存储不可用、unknown 堆积、用量异常和证据缺失。关键事故建议 15 分钟内响应、30 分钟内首次客户沟通；M0 结合值班人数定版。

GA 必须有明确主备值班与升级路径，轮值计划覆盖休假和连续夜间事件；两个人本身不等于可持续 24×7。人力不足时缩小支持窗口或使用已签约托管支持，并匹配客户条款。

手册至少包括：发布/回退、队列重建、旧 worker 隔离、DB 切换、provider 故障、unknown 核对、越权事件、密钥轮换、租户恢复、删除、账单争议和状态页更新。演练可以验证流程；无需等待真实事故发生。

## 14. 安全、审计与数据生命周期（贯穿 W1–W11）

### 14.1 证据可重建

普通运行日志只记录必要标识和脱敏摘要；授权审计存储保留经过变换的完整模型可见输入、工具 schema、模型配置、输出、工具参数和副作用回执。只保存提示词 hash 无法满足重建要求。

分布式 trace 采用 run 内序列、epoch、追加写与外部摘要锚定；对象追加策略和角色隔离配合完整性验证。hash-chain 提供篡改检测依据，不等于管理员绝对无法删改。关键事件不采样丢弃；超过保留期限后的可重建能力如实声明。

### 14.2 威胁与发布检查

必须覆盖越权/IDOR、跨租户缓存和检索、CSRF/XSS、SSRF、提示注入、上传解析滥用、密钥泄漏、恶意连接器、供应链、支付回放、平台运营滥权。公网暴露前有 TLS、请求限制、反滥用、最小权限网络和独立安全测试。

密钥采用托管秘密/KMS、最小授权、轮换及撤销；应用接触短期凭据。每租户密钥按隔离与删除需求选择，不能仅靠密钥名称带 tenant 就声称完整隔离。

### 14.3 生命周期矩阵

| 类别 | 默认规划 | 上线前必须定版 |
| --- | --- | --- |
| 会话与来源证据 | 租户可选保留周期，先以 30 天作容量估算 | 可见范围、版本、撤回、导出与删除 |
| 操作审计 | 比会话更长，严格限制内容与访问 | 安全责任、保留需求、客户查询与销毁 |
| 财务记录 | 按运营地区和实际义务处理 | 主体、币种、保存期限、删除例外与告知 |
| 备份 | 指定可恢复窗口并到期清理 | 所在区域、不可变窗口、删除传播与恢复屏蔽 |
| provider 数据 | 逐模型/地区核对合同与设置 | 是否训练、保留、滥用审查及子处理者 |

删除状态依次记录：禁止新访问 → 活跃存储删除 → 搜索/缓存/导出/连接器清理 → 备份到期或经验证的密码学删除。若历史备份仍包含可解密密钥或明文，就不能声称“销毁当前密钥即不可恢复”。恢复时在开放读取前先应用不可回滚的删除墓碑。

明确隐私说明、客户协议、处理者清单、数据地域及导出/删除流程；地区未知时由负责人组织适用性核对。SOC 2/ISO 等认证按客户要求立项，控制建设与获得外部认证分别记录，不把认证名称作为已经完成的事实。

## 15. 交付、版本和测试体系（W0/W10/W11）

### 15.1 构建与发布

- 保持 Python 3.12、uv 锁定、应用中立内核；重大变更写 ADR，核心不依赖 LangGraph。
- SDK、平台、应用包、schema、API 与配置有独立版本和兼容矩阵。旧运行按创建版本恢复，停止支持前先排空或批准迁移。
- dev/staging/prod 隔离；CI 构建不可变镜像，生成 SBOM、签名和依赖报告，按 digest 晋级。
- IaC 重建环境；密钥从秘密服务注入。生产配置变更留审计，敏感 flag 有所有者与失效日期。
- 数据库迁移采用 expand → backfill → contract，回填可暂停/续跑；混版本 API/worker 兼容性必须实测。
- 灰度从内部租户开始，经 5%/25%/全量等预定步骤晋级；失败停止新增流量，旧运行和外部副作用继续核对。

### 15.2 验证矩阵

| 层次 | 必须运行 | 通过标准 |
| --- | --- | --- |
| 核心回归 | 原质量/SDK/业务/恢复/发行物门禁 | 适用测试通过；纯分支覆盖率至少 85% |
| 存储契约 | SQLite 与真实 PG 对照 | 状态、审批、预算、错误语义一致 |
| 分布式故障 | 崩溃、暂停、分区、租约过期、重复/丢消息 | 无重复副作用、无预算复活、无虚假成功 |
| 租户安全 | 完整入口清单 × 组织/角色矩阵 | 确认的泄漏/越权为零，所有失败分类处理 |
| 业务端到端 | 真实 IdP 测试租户/模型/资料/连接器 | 来源、审批、工单处理和撤回均可验证 |
| 计费 | 重复乱序、迟到、重放、套餐变更、退款/欠款 | 精确计量，未解释差异不出账 |
| 容量 | 基线、峰值、长稳、噪声邻居 | 满足已冻结负载与目标 |
| 运维 | 备份/恢复、升级/回退、告警/支持 | 达到目标并保留时间戳和数据核对 |
| 用户体验 | 未参与开发的用户独立操作 | 关键任务成功率与帮助次数有记录 |

安全测试零失败是发布门槛，不是数学上的绝对安全证明。平均覆盖率不能抵消关键恢复或隔离分支缺测。

### 15.3 业务评估

每个应用先准备分层开发集约 50–80 题，正式集约 80–150 题，具体规模按风险和样本覆盖冻结。包含正常、模糊、无证据、冲突、撤权、注入、超时和重复写；合成题与真实授权业务题分开报告。

引用范围/版本正确率目标 100%，事实正确与恰当澄清/转人工先以 ≥95% 为提案；语义支持、业务成功、时延和成本分别评分。保留分母、失败、未知量、模型版本与评分分歧。正式集不得反复用于调参挑选通过结果。

最终资格遵循仓库完成规则：冻结候选 → 全门禁 → 架构/正确性/安全/依赖/文档审查 → blocker/high 修复与回归 → 新候选 → 干净副本全量复验 → 残余风险与发布签收。

## 17. 日历、人员与成本

### 17.1 时间预算

基础 302–435 人日，加 25% 实施风险缓冲，预算约 **378–544 有效人日**。云账户/采购、数据授权、客户招募、外部审查、完整账期和连续 30 天 SLO 观察构成额外等待；能与开发重叠的部分不重复相加。

| 团队 | 规划周期 | 前提 |
| --- | --- | --- |
| 1 名全职工程人员 | 约 19–28 个月，外部等待另计 | 按 20 有效人日/月；GA 值班仍需额外支持 |
| 3 名专职工程人员 | 约 9–13 个月 | 分工稳定、关键路径不被人力简单平均 |
| 4–5 名专职工程人员 | 约 6–10 个月 | 后端、前端、平台/QA职责齐备，客户与外部支持就绪 |

以上为本项目的规划估算，不是市场统计或交付承诺。M0 完成和 PG/接管原型通过后重新估算一次。

4–5 人团队的参考窗口：第 1 月完成 M0 和事务/租约原型；第 2–3 月实现 M1 和真实业务闭环；第 3–5 月进入 M2/M3；第 5–7 月影子计费转 M4；第 7–10 月完成观察、整改和 M5。前一阶段证据缺失时后移，不靠日期强行发布。

### 17.2 职责

建议 2 名后端（状态与执行/业务与账单）、1 名前端、1 名平台/SRE、0.5–1 名 QA/安全；产品负责人、业务评审人与财务/法务支持按需投入。部分角色可兼任，独立安全复核、实际业务评分和真实使用记录不能由实施者代填。

### 17.3 预算方法

工程预算 = 各角色有效人日 × 内部日成本 + 外部审查/设计支持。月运营预算 = API/worker + PG/缓存 + 对象/日志/备份 + 网络 + IdP/邮件/支付 + 模型 + 支持。

模型成本按每次实际调用的输入/输出/缓存等计费单位求和，包含失败和重试，不再重复乘一个“重试率”。真实单价在供应商选定时获取并版本化。单租户贡献利润 = 收入 − 可归属模型/存储/网络/支付/支持成本；平台总运营成本另外列示。

M0 提交开发、staging、Beta、GA 四档预算；每档设月度告警和硬上限。云服务价格、币种和税费未选定，本文不编造固定金额。

## 20. 风险与范围控制

| 风险 | 提前信号 | 应对与退出条件 |
| --- | --- | --- |
| 状态迁移破坏审批/预算 | 双后端契约差异、未知记录丢失 | 停止切换，固定回归后重冻候选 |
| 旧 worker 发出重复副作用 | 接管测试出现第二回执 | 外部幂等/发送边界核对；无可行保证则限制工具 |
| 业务模型质量不够 | 正式集事实/转人工不达标 | 改开发集与应用方案，使用新独立终评集 |
| 数据或真实客户迟迟未就绪 | M2 前依赖无负责人/授权 | 继续工程验证，业务里程碑明确阻塞 |
| 成本与定价不匹配 | 高分位任务持续亏损 | 配额、价格和模型档位重新评估后验证 |
| 可靠性超出人力 | 告警无人接、夜间积压 | 调整支持范围/增加运维资源，不盲目扩大用户 |
| 保留与删除冲突 | 备份/财务/证据期限互相矛盾 | 冻结数据分类与例外，恢复先检查墓碑 |
| 平台过度复杂 | SDK 出现租户/支付分支、基础设施增多无收益 | 按责任拆分，新增组件需故障/成本依据 |

M6 条件项目：SAML/SCIM（企业客户要求时可提前）、客户管理密钥、专属部署、区域热备、多区域驻留、任意代码沙箱、插件市场、可视编排、多模态和更多计费方式。每项有客户需求、成本和独立验收后进入计划。
