## 2. 本阶段交付的用户闭环

1. 管理员通过离线 bootstrap 建立组织，邀请成员并分配工作空间和已审核部署。
2. 成员登录，切换有权访问的组织，仅看见获授权的工作空间和部署。
3. 成员提交任务；API 原子受理，返回 `202 + run_id`，独立 worker 执行。
4. 成员查看状态、结果与用量，能够请求取消，并理解等待审批、对账中和实际失败的区别。
5. 独立审批人在自己的会话审阅精确动作并批准，worker 继续执行；不共享提交者凭据。
6. 管理员撤销成员、工作空间或部署权限后，下一次受保护访问和下一次实际发送被拒绝；已发生的费用和副作用继续结算。
7. 两个合成应用通过同一套账户、API、工作台、worker 和执行契约，不增加业务特判。

本阶段接受邀请制内部登录适配器；生产 IdP、MFA、恢复和机器身份仍有后续独立验收。内部 Alpha 不直接开放公网客户注册。

## 4. 身份与权限的关键设计

### 4.1 实体与兼容

- 账户使用稳定随机 ID；组织成员关系独立于账户。未来外部身份按 `issuer + subject` 绑定，不按邮箱自动合并。
- 组织是租户边界，工作空间是组织内子范围。部署关联一个明确工作空间和不可变发布版本。
- 身份鉴证与业务授权分开；全局身份查询与租户业务查询采用不同权限合同。
- 旧 `actor_id` 继续保留原含义；不将不同组织的同名 actor 合并，也不重写旧 run owner。
- 不改写 migration 1/2。旧 SDK/commerce SQLite 保持兼容，不建立 SQLite/PG 双主身份库；不自动接管旧治理或业务运行。
- 已有账户接受另一个组织的邀请时，先验证当前账户，再新增成员关系；邀请不能重置已有账户密码、凭同邮箱合并外部身份或误撤销其他组织凭据。

### 4.2 最小权限矩阵

| 主体/权限 | 允许 | 不隐含的权限 |
| --- | --- | --- |
| 组织所有者/管理员 | 成员、工作空间、部署授权管理；敏感操作重验当前权限 | 默认读取全部客户内容或审批业务写入 |
| 部署使用者 | 在获授权范围提交、读取及取消本人运行 | 任意代码发布、修改模型凭据、读取同角色他人运行 |
| 独立审批人 | 读取授权范围内精确待审提案、批准或拒绝 | 自批、使用 owner Cookie、任意执行或组织管理 |
| Worker 服务主体 | 在获准范围竞争 lease、执行和对账 | 人工审批、成员管理、数据库 DDL |
| 身份控制服务 | 受控身份与授权 DML | 迁移所有者权限或任意跨租户业务读取 |
| 迁移主体 | 离线建库/显式升级 | 暴露给公开 API 或普通 worker |

角色只是权限集合，不代表同一个人。旧 `can_execute` 保留后台执行语义，不能直接赋给普通提交者。

### 4.3 发送前的当前授权

- 在权威 PG 的准入和 `mark_sent` 事务内，重查账户/成员、组织、工作空间、部署和授权状态；不能只检查登录会话。
- 受理时冻结部署版本、scope 与配置身份；后续新增权限不会扩大旧 run 范围。
- 撤权后阻止新发送，允许已有物理事实记录与可信对账；unknown 保留预留。
- 会话撤销与权限撤销分别定义：退出使会话失效；组织/成员/部署撤权影响后台执行。不能把两者混为同一种取消。
- 部署停用阻止新受理与新发送；仍有历史读取权限的用户应能查看既有状态、结果和用量，不因当前注册代码缺失而丢失只读入口。
- 对权威检查与网络发送间的在途窗口明确建模，按 PG 准入顺序定义撤权语义；已经进入发送的调用不能保证撤回。
- 无法重验权限时拒绝新的敏感操作；不能从缓存、旧 Principal 或模型文本推断授权。

## 5. API、worker 与页面范围

### 5.1 API 合同

| 入口类别 | 第一版范围 |
| --- | --- |
| 身份 | 登录/退出、邀请接受、`/v1/me`、会话过期与撤销 |
| 组织与成员 | 当前组织列表/切换、受权成员与工作空间管理、部署授权 |
| 部署目录 | 仅列出当前成员可用的已审核部署，不回传代码导入位置或凭据 |
| 运行 | `POST .../runs`、`GET .../runs/{id}`、`POST .../runs/{id}/cancel`；本人运行列表及有界分页 |
| 审批 | 独立待审列表、精确提案详情、批准/拒绝；每次重验当前审批权限 |
| 内部执行 | 独立 worker 入口；普通用户不可访问 `advance` 或注入可信 grant |

客户端仅提交任务、对象选择和幂等键，不能提交可信 actor、角色、scope、预算上限、模型账号或实现导入路径。组织/workspace/deployment/run 的路径组合必须由服务端验证。

默认响应只包含授权的状态、结果、用量及归一化错误；完整 checkpoint/trace 不直接公开。对外错误不回显 SQL、DSN、原始异常或秘密；私有响应采用不缓存策略。写操作验证 CSRF/Origin，Host/CORS 按部署配置约束。

“拒绝审批”是本阶段新增合同，当前托管接口只有 approve/cancel。CP0 需明确持久化拒绝决议、运行收敛状态、权限、幂等与审计；批准和拒绝并发只能一个生效。拒绝阻止提案被消费及后续新发送，已有结果仍须结算，不能仅把页面按钮映射为普通取消而宣称合同完整。

### 5.2 独立 worker

- 第一版复用 PG outbox/扫描，不新增付费队列依赖；并发先固定为 1。
- API 成功受理与任务可被扫描到是同一事务的事实，通知只作提示。
- 采用有界退避、停机停止新领取、lease/epoch 接管和基础运行指标，避免忙轮询及故障反复发送。
- 第一版即设置用户/组织提交速率、待运行数量及总量上限；只有明确授权的内部成员可用。人民币聚合限额完成前，不开放无额度的真实模型调用入口。
- 审批后由 worker 继续；HTTP 请求不直接调用模型/工具。
- 此循环仅证明串行异步托管可用；租户公平、多 worker 容量及完整队列 SLO 在后续验收。

### 5.3 基础工作台

包含登录/邀请、组织与工作空间选择、部署目录、任务提交、本人运行列表/详情、取消、待审队列/审批、成员和部署授权管理。

运行页面区分排队、执行、等待审批、取消处理中、对账中和终态；取消请求不显示为业务已撤回。默认采用状态轮询；SSE/WebSocket、完整 trace 下载和高级报表后续单独授权与验收。

## 6. 必须通过的验收场景

1. 两个组织、两个工作空间、同角色两位用户、独立审批人和服务主体；伪造任何对象路径/正文/标头都不能扩大权限。
2. 登录失败、过期/撤销会话、邀请重放/并发消费、已有账户接受跨组织邀请、CSRF、敏感管理操作及旧 Principal 并发撤权按合同处理；不能重置已有凭据或误撤销其他组织访问，原始秘密不进入日志、trace 或公开错误。
3. API 通过后受理前、排队中、模型返回后工具发送前撤权，均阻止未获准的新发送；已发送 unknown 不记零、不清预留、不自动重发。
4. 同幂等键并发提交只产生一个运行；更改任务、部署、工作空间或 scope 后复用同键发生冲突。
5. 管理员不能因身份管理权限默认批准业务动作；本人不能通过兼任角色自批；审批人使用独立会话，消费指纹与审阅一致；并发批准/拒绝仅一项决议生效，拒绝重放与运行收敛符合新增合同。
6. API 返回 202 后进程退出，独立 worker 仍发现任务；杀死 worker 后新进程接管，恢复旧 worker 不重复业务效果。
7. 连接池复用、错误租户上下文、新表 RLS、身份/执行/迁移不同 PG 角色、列表分页和审计查询真实验证。
8. schema2 历史 owner、审批、receipt、unknown、预算和证据摘要不变；迁移失败回滚，旧 SDK 与参考应用契约保持通过。
   升级前先盘点活跃运行、待审批、unknown 和 outbox，按兼容合同排空或停写迁移；部署下架后，获准的历史只读仍可使用。
9. 两个合成应用使用同一新入口，HTTP 请求/PG 状态/完整证据与独立业务账本一致；使用实际安装的 wheel 验证，不从源码导入冒充。
10. 浏览器完成邀请、登录、任务、审批、取消及撤权流程；页面与 HTTP 权限一致，不以 DOM mock 测试代替最终真实浏览器验收。

每个行为变更和确认缺陷新增有效回归；单元测试、真实 PG 事务测试、真实 HTTP/进程故障测试与浏览器测试各自覆盖相应边界。

## 9. 1000 元/月的执行约束

- 下一阶段先用隔离 PG、确定性模型、回环 HTTP 与合成资料，本地验证不需要购买新云服务。
- 当前整数单位用量不等于人民币预算；S4 完成前，不能称为已有 CNY1000/月硬额度。
- 接入生产前列出已有服务器、数据库、网络、备份/存储、模型和观测的实际月成本，包括包年摊销及预付费消耗；未查明的成本不计为零。
- 先扣除必要固定成本和缓冲，再分配可用模型额度。若固定成本已超过预算，先缩小试点范围或调整资源，不承诺无法覆盖的可靠性等级。
- 人民币准入需包含已结算、在途预留、unknown 和其他共享调用；供应商回执延迟、超出预估或外部未受控消耗仍需对账，不能承诺账单绝不超出估计。
- 建议先设置分级预警、保守的新消耗准入阈值和平台停用开关；具体阈值在实际报价与计量规则接入时冻结。
- 数据库租户隔离、当前授权、精确审批和未知结果不重发不因预算而削减；多 AZ、全天候值班及 SLA 能力必须按实际资金与实测证据声明。

## 10. 执行起点

第一项实施 CP0：冻结账户/组织/workspace/deployment/grant 的实体与权限合同，明确旧 actor 兼容与发送前重验事务，再进入 CP1 的 PG 迁移与仓储实现。

不重复询问已确认的地区、人数、预算和已有资源。供应商配置、实际部署及真实业务选择在对应集成阶段处理；凭据通过本机配置提供，不写入聊天、源码或 trace。
