基线：0.5.0 本地模拟候选、公共 SDK API v1；源码身份 `1aa15ec7599c0f16389cbefc76eb4a0353e9c830cb48c966eae3000fae082241`。

本计划承接 [上一阶段计划](MODULAR_NEXT_PHASE_PLAN.md)、[执行状态](BUSINESS_EXECUTION_STATUS.md)和 [GitHub 对照研究](GITHUB_FRAMEWORK_COMPARISON_2026-10-16.md)。原候选及审计报告继续作为历史基线，新变更必须产生自己的冻结身份与验收证据。

## 1. 目标与交付判断

下一阶段回答两个问题：

1. 在相同业务约束下，ForgeHarness 的权限、资料失效、审批和副作用核对机制，能否带来可复现的正确性或接入成本收益？
2. 一个有实际使用者的业务流程，能否在真实模型、当前身份和授权资料下达到预先约定的质量标准？

默认先做电商咨询试点：理解问题 → 必要时澄清 → 查询当前商品及知识 → 给出有据回答 → 必要时创建待处理工单。法律方向继续承担页级权限、引用与笔记契约的回归验证；真实 LexVault 接入作为有条件的后续分支。

默认顺序来自当前电商闭环较完整这一事实。P0 若确认 LexVault 的资料、只读接口、试用者和专业复核已就绪，而电商条件未就绪，可选择法律作为唯一真实试点，并先补齐其专用评分规则；本轮不同时承诺两条真实业务上线。

最终分别给出三个结论：**工程候选是否通过、指定业务试点是否通过、继续扩展自有运行时是否有证据支持**。任一结论不能代替其他结论。

## 2. 基线与范围

0.5.0 已有的证据：源码和独立干净副本各通过 978 项测试、72 项门禁；干净副本纯分支覆盖 86.925%。40 法律＋80 电商场景属于合成开发契约；63 项选定安全回归已通过；60 个合成封存夹具未用于终评。[候选审计](business-release-audit.json)

本轮直接复用会话、资料版本、导入、任务、授权检索、审批、回执和追踪能力。开发范围集中在公平对照、接入简化、通用工单、自然语言澄清、真实身份/资料适配和验收证据。

暂不立项：新增多 Agent 编排模式、微调、通用分布式平台、完整法律工作台迁移、支付退款改价、真实平台消息自动外发、视频流程。只有试点失败或负载证据直接要求时，才另立小范围变更。

核心继续使用 Python 3.12 与 `uv`，保持框架独立；对照项目放在可选的隔离环境，不将 LangGraph 引入核心依赖。非平凡架构变化记录 ADR，行为变化和确认缺陷增加回归测试，借鉴上游实现保留出处。

### P1：公平对照与接入体验

主要对象为 ForgeHarness、[Deep Agents](https://github.com/langchain-ai/deepagents) 和 [Pydantic AI / Harness](https://github.com/pydantic/pydantic-ai)。其余项目用作设计参照，本轮不扩展成六框架全量竞赛。执行前重新核实上游实际包、接口、稳定版本及持久化要求，固定版本、提交和锁文件；当前研究记录见 [来源清单](GITHUB_COMPARISON_SOURCES_2026-10-16.json)。

**公平规则**：

1. 使用相同资料、业务工具行为、任务输入和期望状态。相同模型与可比采样参数、上下文/输出/工具调用预算；不支持的参数或额外模型调用单独披露。
2. 每个框架使用其推荐的持久化、审批和后端配置。需要额外服务时记录资源和部署成本；配置未完成记为“未测”，不能记为框架失败。
3. 分别报告最小接入配置与达到相同业务契约的配置。每项保障注明由“上游原生 / 共享宿主 / 专用适配 / 自有运行时”哪一层实现；共同宿主提供的保障不能归功于某一框架。
4. 确定性故障测试使用统一事件顺序与故障点；真实模型质量测试允许各框架必要的系统提示差异，但保存实际模型输入，不额外给某一方答案或任务线索。
5. 同一环境规格、工具延迟和数据版本；声明并固定冷/热启动、缓存、并发、运行顺序和重试口径。设置独立运行目录，隔离不同框架状态。
6. 对照报告包括全部失败、未测项和支持边界。测试通过只代表所测场景，不作一般性安全、性能或市场成熟度排名。

**必须覆盖的故障场景**：

| 场景 | 故障注入点 | 可观察验收结果 |
| --- | --- | --- |
| 等待期间撤权 | 模型调用前的资料等待或审批等待 | 撤权后的内容不进入模型或对外返回，后续动作被拒绝 |
| 资料撤回后追问 | 已产生历史之后撤回或换版 | 陈旧来源及派生历史不再作为可用证据；正常有效资料仍可使用 |
| 审批参数变化 | 审批后修改参数、身份或作用域 | 旧审批不能授权变化后的动作；原动作的合法审批可继续 |
| 写入成功但回执丢失 | 业务写入落地后、运行证据保存前 | 查询现有结果或进入待核对，不盲目重写、不虚报成功 |
| 重复请求 | 并发提交以及重启后重发 | 绑定稳定请求/业务键；冲突内容拒绝，同一业务效果只发生一次 |
| 取消与写入竞争 | 写入前、写入中、写入完成后 | 报告实际完成、取消或待核对，不把取消说成回滚 |

在适用场景覆盖正常对照、故障、进程重启与重复执行。采用台账状态、工具实际调用与模型实际输入作判定依据；单看最终回答或异常类型不够。既有跨租户、注入、预算和证据删除回归继续保留。总是拒绝的实现不能因安全负例通过而取得合格结论。

**接入体验试验**：在独立练习目录中完成“授权只读助手”和“独立审批写入助手”。由未参与该接口实现的开发者按文档接入；记录主动开发时间、额外服务、业务代码与框架适配代码、错误配置、首次成功时间、最终契约结果。说明人员既有经验和试验顺序，人数少时仅报告个案，不能声称统计显著。无人可参与时可做自测，但明确独立接入验证缺失。

**验收与停止点**：产出可重跑协议、各实现版本/配置、受控原始结果和差异归因。结论分为三类：有效对照支持自有核心收益；有效对照未显示收益；因配置、覆盖或人员缺失而证据不足。前两类形成架构取舍 ADR，最后一类登记补测缺口，不据此宣告任一方案胜出。尚无有效收益证据时暂停扩大核心功能，可继续补测与当前业务适配。

本候选及共同测试基座的 blocker/high 必须修复后晋级。其他对照实现的问题按事实保留；配置错误应修正并记录复测，未解决的问题按预先规则记失败或未测，不要求先修完上游项目才能继续本项目的独立工作。

### P2：补齐一个业务闭环

以下清单适用于默认电商试点。若 P0 选择法律，须在 P0 用 LexVault 只读身份/页级适配、撤回传播、原流程同题对照、待审笔记及专业评分的专用清单替换本节电商任务；模型接线、可读界面和迁移验证保留。电商通用工单等缺口转入后续项，不成为法律试点的前置要求。

1. **无商品通用工单**：定义无 SKU 工单的业务身份、幂等键、租户权限、最少上下文及缺证据原因。允许在没有商品证据时请求人工，不虚构商品和引用；明确无商品资源授权方式，不能以缺 SKU 绕过权限。保持申请人与审批人的独立性。
2. **自然语言澄清**：对商品不明确、指代不明、信息缺失与资料冲突分别定义处理规则。系统记录澄清进度、轮次上限及已确认商品；达到上限提供人工路径。模型负责提出问题，确定性状态与工具负责约束执行。支持用户纠正和切换商品，不能沿用失效来源。
3. **真实模型接线**：复用已有模型协议与适配器，记录实际请求、模型/参数、工具轨迹、真实用量与失败。设置单次输出、总调用量和墙钟边界；资源不足、超时或结构无效必须可区分，不能返回模拟答案冒充模型结果。
4. **界面与接入简化**：用商品、价格、库存、查询时点、依据、待处理状态和下一步替代原始 JSON；内部哈希与调试字段放入受控诊断入口。补一份最小接入示例，通过显式配置减少样板代码，不能隐藏必需的授权/来源校验。
5. **可重启与迁移**：涉及工单字段或持久状态变化时，先确定 schema 兼容和迁移/回退办法。用旧格式状态副本验证重启，不能直接覆盖唯一业务状态。

**验收**：所选清单的正常和失败路径都有回归；旧六条演示继续运行。电商覆盖无证据、明确要求人工、来源冲突及重复工单控制；法律按替换清单验证当前页级权限、引用定位和笔记状态。模型的业务表现另按 P3/P4 的对应评分，不以确定性回归替代。

### P3：真实身份、资料与受控试用

- 接入宿主当前认证身份和资源授权；租户、角色、资源范围由服务端获得。公开演示角色名仅用于演示环境。验证撤权、离职/禁用、跨租户请求与审批人变化。
- 商品与库存先接入只读接口，记录来源、版本或查询时点；知识资料走既有审核发布链。接口缺失、超时、陈旧或冲突时，按明确策略澄清/拒答/转人工。
- 工单先落受控测试台账或内部待处理队列，由实际人员查看和处理。只有外部系统的权限、幂等和核对方式明确后，才另行接通真实外部写入。
- 在许可范围内用真实问题开展限定试用，记录未答、误答、不必要澄清/转接、处理耗时和用户是否完成任务。建议至少两名实际使用者、30 个有完整记录的会话作为可用性观察；该数量只用于发现问题，不作为生产成功率证明。
- 法律试点若被选中：沿用原系统身份与页级权限，先做只读同题对照；待审笔记独立存放并经内容审核，不自动覆盖原案卷。需专业人员复核结论与引用适用性。

**验收**：选定业务的角色、资料版本、来源撤回、失败路径和人工处理均有实际记录；有操作说明和回退步骤。停用新入口、切回原流程、保留台账并核对在途请求，是回退的默认操作；不能靠删库消除问题。

### P4：冻结候选与终验

- 固定源码身份、依赖版本、模型及参数、资料摘要、评分版本和候选范围；任何受测实现变更都会产生新候选。
- 对架构、正确性、权限与隔离、依赖、测试、文档和对外能力描述做完整审查。确认的 blocker/high 修复并加回归后，重新冻结。
- 运行适用于新范围的全套门禁，至少保留原质量/安全/兼容要求；核心纯分支覆盖不低于 85%。从干净副本复验，核对 wheel/sdist 文件与资源，再做最小安装和演示。
- 满足第 4 节条件后执行一次终评；完整保存预定批次的成功、失败和中止证据。未通过可继续开发，但重测需新的独立封存集与声明。
- 分别发布工程审计、业务试点结论、对照结论和剩余风险。测试数及用例数以实际结果填写，不预设要超过 978 才算进步。

## 4. 评测数据、预算与验收规则

### 4.1 三类数据分开管理

| 数据 | 用途 | 规则 |
| --- | --- | --- |
| 既有合成契约与新增故障场景 | 稳定验证状态、权限、来源和副作用 | 可反复运行；不等同于独立业务题或专业判断 |
| 真实业务开发集 | 接线、模型选择、提示与流程调试 | 电商目标至少 80 道独立题，记录资料族/来源；法律若为主试点则整理 30–50 道开发题 |
| 独立终评集 | 冻结后的业务验收 | 电商另建至少 60 道新题；法律题量与评分由专业复核者在开发期确定，不能临时以合成题替代 |

终评由未参与模型/提示调优的人员整理和保管，按商品族、案件和来源分组切分，检查开发集与终评集的重复及近似泄露。缺少独立整理条件时，结果只能称内部评测。

已有 60 个机器生成的合成封存夹具保持原状态及治理规则，不直接升级为专业终评证据。独立题目数、每题重复采样数和总模型运行数分别报告。

### 4.2 先固定评分，再打开终评

以下为本计划提出的电商验收草案，需在 P0 明确业务含义，在开发阶段完成评分校准，并在首次打开终评之前形成不可覆盖的正式声明。

| 指标 | 提议标准 | 判定口径 |
| --- | --- | --- |
| 跨范围泄露、未授权动作、重复副作用、虚假完成 | 0 起 | 任一确认事件立即中止放行并登记缺陷 |
| 引用/来源有效性 | 有引用的题全部通过精确定位、权限与版本检查 | 不验证法律推理；关键来源缺失不能用少给引用掩盖 |
| 事实正确性 | ≥95% | 以题为单位，全部关键事实正确才通过；可回答却拒答或漏答的题计失败 |
| 澄清恰当性 | ≥90% | 对预先标注的需要/不需要澄清两类分别报告；同时报告多余澄清与澄清后任务完成率 |
| 人工转接 | 精确率、召回率均 ≥95% | 分母来自预先标注的应转/不应转案例，数量不足时不宣告达标 |
| 时延与用量 | P0 提出目标，开发期校准，终评前冻结 | 分别报告 p50/p95、失败/超时、真实 token、工具调用量；试验环境和样本量同时记录 |

关键事实、该拒答/澄清/转接的条件与最低样本覆盖必须写入评分细则。未执行、超时及评分失败保留在总数中并按预设规则计分；不能只计算成功回答。报告比例时给出分子、分母和不确定性，不用小样本宣称接近零的线上事故率。

终评声明至少绑定：应用/源码/依赖、模型标识和参数、预算、资料/题目摘要、评分细则、评审者、采样计划、中止条件及时间。若计划每题多次采样，应一次性预先声明完整批次；首次打开后不得查看结果再改参数择优重跑。中断或失败也记录消费状态。

模型裁判可以辅助分类，关键事实及争议题需依据来源复核；法律专业结论需独立专业评审。真实模型结果不得用模型自评直接替代验收。

### 4.3 资源约束

执行前记录可用模型、运行位置、机器内存/并发限制、单轮与整批预算。付费调用的支出上限尚未确定时，继续确定性工作和离线接线，待上限明确后开展付费评测。已有本地模型也须设置请求输出上限与批次规模，避免重现历史资源耗尽。

先小批开发测试估算资源，再提交完整批次的调用量与费用估算；估算不是实测成本。本计划不指定未经核实的模型价格或绝对时延承诺。

### 4.4 运行证据与真实资料的保存边界

认证凭据、模型密钥和原始秘密不得进入模型输入或轨迹。真实授权资料及完整运行证据保存在明确允许的受控位置，配置访问权限、保留期限和删除规则；仅在已确认的模型处理位置使用。能够在授权范围内重建实际输入、工具效果与状态转换，同时验证脱敏和来源绑定没有破坏证据一致性。

仓库及可公开报告只保存脱敏摘要、指标、必要的摘要值和受控证据引用；下面列出的 `reports/` 产物是报告索引，不是默认存放真实原文或完整私有轨迹的位置。发布安装包、报告或示例前检查其成员，排除私有材料和凭据。

## 7. 工作量、停止点与取舍

以下为规划估算，包含实现、回归与文档，不含授权等待、第三方评审排期及不可预知的上游故障。P1 完成后按实际接入成本重估。

| 阶段 | 预计有效工程工时 |
| --- | --- |
| P0 范围与协议 | 8–12 小时 |
| P1 三方对照与接入试验 | 24–40 小时 |
| P2 业务缺口与接线 | 24–40 小时 |
| P3 真实试点适配与开发评测 | 24–48 小时 |
| P4 冻结、终验与修复 | 16–28 小时 |
| 合计 | 96–168 小时；另预留约 20% 修复缓冲，总计约 115–202 小时 |

按每周 20–25 个有效工程小时，约 5–10 周；这是工作量推算，外部条件和复核安排可能延长日历时间，不作为交付日期。

阶段停止规则：

- **安全/正确性停止点**：本候选或共同测试基座发现当前范围内的越权、重复副作用、虚假完成或其他 blocker/high，停止放行，先修复、回归、重新冻结。对照项目的未解决问题保留为比较证据，不自动阻断本项目无关工作。
- **证据停止点**：独立资料、真实模型或专业复核缺失时，只交付已通过的工程范围，业务验收标为未完成。
- **架构停止点**：有效对照未显示自有运行时收益时，停止扩张并评估组件化集成；证据不足时暂停扩张、登记补测项，不作胜负结论。两种情况下均可保留资料治理、审批契约与评测资产。
- **发布停止点**：干净复验、安装验证或正式业务门槛未通过时，保留失败证据并继续修复，不沿用 0.5.0 审计为新代码背书。

本阶段成功的标志，是取得可复查的差异证据并完成一个范围明确的真实试点；功能数量、测试数量或多 Agent 数量都不单独作为完成标准。
