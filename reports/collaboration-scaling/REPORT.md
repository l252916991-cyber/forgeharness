# 多 Agent 协作值不值得：按材料规模的对照实验

日期：2026-11-07（Asia/Shanghai）。模型：`deepseek-flash`（温度 0，关闭思考，单次输出上限 1024 token）。
脚本：`benchmarks/experiments/scaling.py`；题目：`evals/audit_tasks.py`。

> 0.14.0 起，实验脚本整理进 `benchmarks/experiments/`，三套题目生成器合并为 `evals/audit_tasks.py`（生成的题目逐字节不变）。封存协议记录的脚本哈希对应提交 `ef54942`；要按封存校验复现，请先 `git checkout ef54942`。

**结论**：在这个任务上，固定专家协作（team）在任何规模都不值得。按事先封存的判定规则，
N = 4、8、16、32 全部判为 `team_not_worth_it`。

- 最好的方案是最简单的 **oneshot**：程序确定性地读完全部材料，只调一次模型。它在每个规模都是 8/8，
  延迟约 1 秒，成本最低。
- **team** 在 N ≤ 16 时同样全对，但成本是 oneshot 的 3.7–5.0 倍；到 N = 32 降到 1/8。
- team 的设计目标确实做到了。单次请求的最大 prompt 始终在 2.8k token 以内，而 N = 32 时
  oneshot 是 13k，ReAct 是 15k。N ≥ 16 时 team 也比 ReAct 快：N = 16 时延迟是 ReAct 的 0.60 倍，
  N = 32 时是 0.31 倍。但即使在 N = 32，全部材料也只有约 13k token，远没到一次上下文装不下、
  或者质量开始下降的程度，所以隔离换不来收益。

## 实验设计

**任务**：审计 N 份互相独立的服务配置，找出所有违规的服务。规则有三条：

- R1：重试大于 0 的接口必须幂等；
- R2：超时不超过 30 秒；
- R3：连接数不超过 64。

每份配置最多违反一条规则，并带有两类干扰：恰好在边界上的合规值（30s、30000ms、64），
以及提到旧的违规值的 changelog。答案是一个服务 ID 集合，与标准答案完全一致才算成功。
题目是作者用固定随机种子生成的合成数据；单元测试用一套独立的规则检查器核对了每个标签，
并确认没有材料会被凭据脱敏改写。

**三个方案**：同一模型、同一规则文本、同一答案格式。三个方案的循环内都不给正确性反馈（verifier 全部放行）。

| 方案 | 做法 |
|---|---|
| ReAct | 单个 Agent 用 `read_material` 逐份读取，最后给出答案 |
| oneshot | 程序通过 kernel 读完全部材料，然后只调一次模型（不带工具） |
| team | 现有的 `Collaboration`：min(8, N) 个专家，每人分到 ceil(N/8) 份材料，最多 2 个模型调用并发；最后由 coordinator 合并各专家的报告 |

**流程**：

1. 先在 dev 集上调通。
2. 封存方案 `protocol.json`，其中绑定了脚本和题目的哈希、模型、采样数和判定规则。
3. 正式集只跑一次：每个规模 4 道题、每道题采样 2 次，每个方案在每个规模跑 8 次，共 96 次运行。
4. 运行顺序按题目和采样轮换，避免某个方案总是先跑、吃到冷缓存。

**判定规则**（封存前写定）：先在 ReAct 和 oneshot 中选出成功率更高的一个作为「最好的单 Agent」，
成功率相同时选成本更低的。满足下面任一条件，就判定 team 值得：

- team 成功率 ≥ 最好的单 Agent，且 p50 延迟 ≤ 它的 0.8 倍，或每次成本 ≤ 它的 0.8 倍；
- team 成功率比最好的单 Agent 高至少 0.25。

成本按 DeepSeek 公布的高峰价估算，按缓存命中和未命中分开计算。这是用于比较的估算，不是账单。

| 4 | oneshot | 8/8 | 1.000 | 0.8 秒 | 1 | 1,844 | 0.0003 |
| 4 | team | 8/8 | 1.000 | 4.8 秒 | 5 | 1,407 | 0.0015 |
| 8 | ReAct | 8/8 | 1.000 | 8.0 秒 | 9 | 4,456 | 0.0014 |
| 8 | oneshot | 8/8 | 1.000 | 0.8 秒 | 1 | 3,471 | 0.0006 |
| 8 | team | 8/8 | 1.000 | 7.9 秒 | 9 | 2,149 | 0.0029 |
| 16 | ReAct | 8/8 | 1.000 | 14.8 秒 | 17 | 8,038 | 0.0029 |
| 16 | oneshot | 8/8 | 1.000 | 0.9 秒 | 1 | 6,780 | 0.0011 |

## team 在 N = 32 为什么失败

**错误全部出在专家层，coordinator 没有出错。** 7 次失败的运行中，专家一共漏报 8 个服务、误报 1 个。
coordinator 每次都把专家报告原样合并，没有漏掉也没有多加，7/7 次如实合并。

**错误类型**：9 个错误里，6 个是 R1 漏报，1 个是 R3 漏报，还有 1 个是误报：svc-15 的取值全部在边界上，
其实是合规的。R1 需要把 headers 对应到同一个接口块，是三条规则里最依赖结构化阅读的一条。

**与负载的关系**：

| N | 专家每人材料数 | team 的服务级错误 | oneshot 的服务级错误 |
|---|---|---|---|
| 4 / 8 | 1 | 0 / 32、0 / 64 | 0 |
| 16 | 2 | 0 / 128 | 0 |
| 32 | 4 | 9 / 256 | 0 / 256 |

这里有一个说不通的地方：oneshot 一次读完 32 份材料（13k token）一个都没错，专家每人只读 4 份却会出错。
所以原因不是「材料太多看不过来」。

**可能的原因**：本实验没有做消融，下面三条只是假设，都未验证，不下结论。

1. 专家必须输出结构化的 AgentReport：先写一段总结，再写每条发现及证据 ID。单 Agent 只输出一个 ID 列表。
   8 次漏报里，专家每次都在总结中把被漏的服务和别的服务合成一句，判为合规，例如
   `svc-18 and svc-19 are compliant.`；后面的 findings 和总结保持一致。
   这说明错误在写总结时就已经定下了，但不能证明是这种输出格式导致的。
2. 协作节点的消息顺序是：用户消息（规则）→ 系统消息（专家指令和完整的 JSON schema）→
   用户消息（材料）。系统消息不在开头，而 ReAct 和 oneshot 的系统消息都在开头。
3. 两次采样不是独立重复。温度为 0，同一道题的两次采样高度相关，例如 n32-2 的 svc-19、n32-4 的 svc-32
   两次都被漏掉。因此每个规模的有效样本更接近 4 道题，而不是 8 次运行。不过 team 在 4 道题里都至少失败了一次。

ReAct 在 N = 32 失败的 2 次是同一道题（n32-3）：两次采样都漏了 svc-26，也是 R1。

## 基础设施与可重复性

**第一次 dev（11-03）**：

- 一次 ReAct 运行遇到 HTTP 503；
- 两次 team 运行被单个模型调用拖慢。一次是 coordinator 等了 69 秒；另一次是两个并发调用同时卡了约 94 秒。
- 同期框架自身每次状态转移不到 0.1 秒。

据此修改了脚本：

- 遇到 429、5xx 或请求没有响应时，从全新状态重跑，最多 3 次。只按最后一次评分，每次尝试都保留。
- 记录每次调用从请求到收到响应头、到收完响应的时间，用于区分服务商的延迟和框架开销。

改完后重跑 dev（dev2），再从 dev2 封存方案。第一次 dev 的结果保留作为记录。

**正式集（11-07 17:50–18:03）**：

- 800 次模型调用，p50 1.06 秒，p95 1.86 秒，最慢 3.3 秒；
- 没有超过 30 秒的调用，也没有重试；
- 总成本约 0.24 美元（按高峰价估算）。

第一次 dev 中的卡顿在正式集没有再出现，从客户端无法判断原因。

**校验**：

- dev2、正式集和协议里的脚本与题目哈希都与当前代码一致；
- `summary.json` 可以从 96 个 `result.json` 原样重算出来；
- 提交的 9 个 trace 都通过了哈希链校验。

**复现**（需要自己的 DeepSeek key，放在 `FORGE_API_KEY` 环境变量里；协议文件不可覆盖，复现时要换一个新的协议路径）：

```bash
uv run --no-sync python -m benchmarks.experiments.scaling --split dev --mode live --samples 1 --output reports/collaboration-scaling/<新目录>
uv run --no-sync python -m benchmarks.experiments.scaling --seal --dev-report reports/collaboration-scaling/<新目录> --protocol <新协议路径>
uv run --no-sync python -m benchmarks.experiments.scaling --split evaluation --mode live --samples 2 --protocol <新协议路径> --output reports/collaboration-scaling/<另一个新目录>
```

不需要 key 的接线检查可以用 `--mode contract`。这个模式用一个总会答对的模型代替真实模型，结果永远不算测量。

## 局限

- **只测了一个模型、一种合成任务。** 材料之间完全独立，这是最适合拆分给多个专家的情况；
  而且材料总量远小于模型的上下文窗口。
- **team 只测了一种配置**：最多 8 个专家、并发 2。没有测其他专家数量或每人负载的组合。
- **样本量小**：每个规模 4 道题，属于探索性实验，没有做多重比较校正；温度为 0 时两次采样相关。
- **成本是按公开价格估算的，不是账单。**
- **不能推广成「多 Agent 没用」。** 本实验没有覆盖这些情况：材料总量超出一次上下文；
  子任务需要不同的工具或权限；任务需要写操作隔离。这些情况下结论可能不同。

## 对项目的意义

AGENTS.md 要求多 Agent 能力「靠评测证明自己的复杂度」。这是第一份针对协作模块质量的真实模型对照：

- 材料能装进一次上下文的审计类任务，应该用 oneshot。
- 协作模块的长处（上下文隔离、并行降延迟）确实测到了，但在这个任务里只体现在和 ReAct 的对比上，
  抵不过 oneshot。
- team 在 N = 32 的失败原因，本报告写作时还没有定位。后来在一组新题上做了消融，见
  [消融实验](../collaboration-ablation/REPORT.md)：按预注册规则没有一个变体被判为「消除失败」；
  系统消息挪到最前面反而更差，先写结论再写总结则让漏报消失，但这个变化不显著。
