# 改进计划书：协作「应该赢」的场景——长上下文规模实验

日期：2026-11-07（Asia/Shanghai）。状态：本计划已按原样封存并执行，结果见同目录 [REPORT.md](REPORT.md)。

> 0.14.0 起，实验脚本整理进 `benchmarks/experiments/`，三套题目生成器合并为 `evals/audit_tasks.py`（生成的题目逐字节不变）。封存协议记录的脚本哈希对应提交 `7f32d0d`；要按封存校验复现，请先 `git checkout 7f32d0d`。

## 1. 背景

前两轮实验在同一类审计任务上得出：

- 材料总量在 13k token 以内（≤ 32 份）时，「一次调用」16 道题全对，固定专家协作在任何规模都不值得
  （[规模实验](../collaboration-scaling/REPORT.md)）；
- 专家漏报的原因没有找到达到判定门槛的解释（[消融实验](../collaboration-ablation/REPORT.md)）。

这两轮只回答了一半的问题：**材料装得进一次上下文、而且模型一次读得过来时，协作没有必要。**
另一半没有回答：材料多到一次调用开始读不准时，拆分给多个调用（或多个专家）能不能赢回来？
这是多 Agent 协作最常被引用的理由，也是本项目协作模块存在的前提。

## 2. 要回答的问题

1. **一次调用从多大规模开始变差？** 把材料从 32 份（约 13k token）加到 1024 份（约 420k token）。
2. **变差时，拆分能不能恢复准确率？代价是多少？**
3. **如果拆分有效，需要协作框架（专家 + coordinator），还是程序层面的简单拆分就够？**

## 3. 不做什么

- **不测 ReAct。** 1024 份材料需要 1000 多个串行步骤，上下文涨到 40 万 token，时间和费用都不现实；
  而且 32 份时它已经不如一次调用（6/8 对 8/8）。
- **不测超出模型上下文窗口的情况。** `deepseek-flash` 的窗口约 100 万 token（第三方文档；dev 会实际验证
  42 万 token 的请求），超出窗口时一次调用直接无法运行，结果是确定的，不需要实验。
- **不测需要跨材料推理的任务**（例如「依赖了违规服务的服务」）。任务保持不变，才能和前两轮比较。
  这类任务是协作可能真正有优势的另一种场景，留作后续。

## 4. 任务与数据

- 同一个审计任务、同一套三条规则、同一个材料生成器。生成器原来只有 40 个服务名，最多生成 40 份；
  新模块 `evals/audit_tasks.py` 在名字后面加编号来扩充，其余生成逻辑完全复用。
- 规模：N = 32、128、512、1024，约 13k、53k、211k、422k token。
- 种子：dev 4401（每个规模 1 道题），正式集 5502（每个规模 4 道题）；每道题每个方案只跑一次
  （温度 0，前两轮已经看到两次采样高度相关）。
- 单元测试确认：新题和前两轮的所有材料都不重复；每个标签都通过独立规则检查；没有材料会被凭据脱敏改写。

## 5. 三个方案

| 方案 | 做法 | 每次运行的模型调用 |
|---|---|---|
| oneshot | 读完全部 N 份，一次调用 | 1 |
| split-32 | 每 32 份一组，每组就是前两轮验证过的 oneshot（32 份时 16/16 全对）；最多 8 组同时进行，程序合并答案 | N/32：1、4、16、32 |
| team-16 | 每 16 份一个协作方案：8 个专家各 2 份 + 1 个 coordinator（消融中最好的协作配置，11/12）；最多 4 个方案同时进行（每个方案内部最多 2 个调用并发，总计不超过 8 个），程序合并各方案答案 | 9N/16：18、72、288、576 |

**为什么 team 要在程序层面分组**：现在的协作模块一个方案最多 32 份材料、8 个专家、每个专家 8 份、
coordinator 报告最多 30 条结论。超过 32 份就必须由程序把多个方案拼起来。这本身也是要记录的事实：
协作模块不能原生扩展到大规模材料。

所有调用使用同一模型、同一规则文本、同一答案格式；单次输出上限从 1024 提高到 4096 token
（1024 份时，一次调用要输出约 300 个 ID），所有方案相同；每个 HTTP 请求超时 600 秒。

## 6. 指标与判定规则（封存前写定）

**评分**：

- 按集合比较（ID 超过 99 后，字符串排序和编号顺序不同，不能再按顺序比较）。
- **主要指标：服务级错误率** = （漏报 + 误报）/ 判断次数。判断次数 = N × 题数。
  1024 份材料时，一个错误就会让整题判错，所以整题成功只作为次要指标。
- 任何一个单元（一次调用、一组、一个协作方案）没有给出可解析的答案，就视为该单元什么都没报：
  其中的违规服务全部算漏报，并单独报告失败单元数。
- 成本和延迟只做描述，不进入判定。

**判定**：

- **一次调用变差**：在某个 N（N > 32），oneshot 错误数 ≥ 10，且错误率 ≥ 0.5%。
- **拆分值得**：在某个 N，oneshot 错误数 ≥ 10，且该拆分方案的错误数不超过 oneshot 的一半。
- **框架 vs 程序**：在某个 N，
  - split-32 错误数 ≥ 10，且 team-16 不超过它的一半 → 框架更好；
  - team-16 错误数 ≥ 10，且 split-32 不超过它的一半 → 程序拆分更好；
  - 其余情况 → 没有明显差别。
- 如果没有任何 N 满足「一次调用变差」，结论就是：在这个任务上，一次调用能处理到约 42 万 token，
  拆分没有质量上的理由。

**测量有效性**：数据完整；重试后没有基础设施错误；trace 全部通过校验；用量全部已知；运行期间源码未变。
基础设施重试规则沿用前两轮：遇到 429、5xx 或无响应时，从全新状态重跑，最多 3 次，只按最后一次评分，所有尝试都保留。

## 7. 流程

1. **contract 模式**：不需要 key，用一个总会答对的模型代替真实模型，跑通全部规模和方案。
2. **dev**：每个规模 1 道题，每个方案各一次。
3. **封存**：dev 必须是有效测量，且每个单元都给出了可解析的答案，才允许封存方案；
   否则先检查原因（例如输出被截断、请求超时），修正后重跑 dev。
4. **正式集**：每个规模 4 道题，每个方案各一次，共 48 次运行，只跑一次。
5. **分析与报告**：从结果文件重算汇总，按封存的规则判定，写报告，更新文档。

## 8. 成本与时间估计

按 DeepSeek 高峰价、不计缓存估算（单材料约 412 token）：

| 方案 | 每组题（4 个规模各 1 道）的输入量 | 估计费用 |
|---|---|---|
| oneshot | 约 70 万 token | 约 0.21 美元 |
| split-32 | 约 72 万 token | 约 0.22 美元 |
| team-16 | 约 200 万 token + 约 17 万输出 | 约 0.6–0.8 美元 |

- dev 1 组 + 正式集 4 组，共约 5–6 美元（高峰价）；非高峰时段（工作日 9:00–12:00、14:00–18:00 以外，以及周末）
  价格减半，约 2.5–3 美元。
- 时间：dev 约 8 分钟，正式集约 30–40 分钟。建议用 macOS 的 `caffeinate -i` 运行，防止电脑睡眠打断。
- 框架自身的开销：contract 模式不调用真实模型，在云端环境测得协作框架每个节点约 0.35 秒 CPU 时间，
  主要花在持久化和 trace 上；1024 份时 576 个节点约 200 秒。这部分会计入 team-16 的延迟，
  报告中会单独列出。

## 9. 风险与应对

| 风险 | 应对 |
|---|---|
| 42 万 token 的请求超时 | 请求超时设为 600 秒；超时按基础设施错误重试 |
| 一次调用输出被截断，JSON 不完整 | 输出上限 4096；若仍截断，在 dev 阶段暴露，封存会被拒绝 |
| 8 个并发调用触发限流 | 沿用 429/5xx 重试规则；dev 会先暴露 |
| 错误集中在少数题目上 | 报告按题列出错误分布；结论标明是探索性的 |
| 判定门槛设计不当（上一轮的教训） | 本次用错误数和错误率定门槛，不再用「多对几题」 |
